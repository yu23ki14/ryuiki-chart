# P5 — 失敗のトリアージ

対象: `data/db/cells.sqlite` の `cells` / `extraction_log` テーブル（P1 Maker + P2 Checker、
2026-08-29 時点、対象PDF26本のうち表が検出された20本・327表・55,305セル）。

集計:

| チェック | 失敗件数 | 対象セル数に対する割合 |
|---|---:|---:|
| C1 (source_text の実在) | 0 | 0.0% |
| C2 (value_raw が source_text に含まれる) | 19 | 0.03% |
| C3 (value_raw と value_type の整合) | 0 | 0.0% |
| C4 (unit が語彙辞書に存在) | 0 | 0.0%（注: 判定対象はunit付与済みセルのみ。後述） |
| C5 (合計行の内訳一致、相対誤差0.5%許容) | 615 | 1.1% |
| C6 (row_key/col_key の取り違え) | 3,907 | 7.1% |

全55,305セル中50,827セル(91.9%)がC1〜C6すべてを通過。**C1（幻覚の直接証拠）は0件**——
Makerがsource_textを生テキストからのliteral検索でしか作らない設計のため構造的に発生しない。
失敗の大半はC6（行/列キーの構造的な取り違え）とC5（合計不一致）で、これはLLMの幻覚ではなく
**pdfplumberの罫線ベースの表分解が、複雑な多段見出し・縦書きラベル混在の表で破綻する**という、
決定論的パイプライン固有の限界を反映している。

## A. 辞書不足

P0で収集した語彙(`data/vocab/vocab.json`, 124 unit語)のうち、Makerの`UNIT_TOKENS`
（半自動判定に使う固定リスト）に含まれていないものが29種見つかった。C4は
「unit列に値が入っているセルのみ」を判定するため、そもそもunitを拾えていない
セルはC4をすり抜けて「失敗として顕在化しない」——これ自体がA類の典型的な症状。

代表例:
- `tanzawa_shika_r6` p.26: `頭/km` （シカ生息密度。Makerの辞書には`頭/km2`しかなく`頭/km`が漏れていた）
- `suigen_hozen_final_eval` p.58: `糞塊数/km`（シカの糞塊密度指標。とても具体的な単位で辞書化されていなかった）
- `suigen_hozen_final_eval` p.100: `万人`, `℃`（経済評価アンケートの回答者数、水温）

見つかった未収載単位の全リスト（P0が収集した語彙 - Makerの固定辞書）:
```
cm, mm, kg, kg/月, m3/日, t, ℃, GLm, 万m3, 千m3, 万人, 千人, 人,
円/月・世帯, 回/年, 本/ha, 糞塊/km, 糞塊数/km, 頭/km, 頭/人・日,
万個/mL, 個/mL, 千/mL（千/mℓ）, 種類, 目, 科, 綱,
●（確認地点マーク）, -（地点非公開マーク）
```
（末尾4つは単位ではなく凡例記号。P0のunits抽出プロンプトが「量の単位」以外の
記号も拾ってしまった誤収載で、辞書パッチではなく抽出プロンプト側の精度課題）

文脈に限定するなどの追加ロジックとセットでの導入を推奨する。

## B. OCR品質（テキスト抽出順序の破綻）

このプロジェクトの対象はスキャン画像ではなくデジタルPDFなので、文字自体が潰れている
古典的なOCR品質問題は見られなかった（`unreadable_reason`はすべて「文字化け」ではなく
「literal一致が取れない」ケース）。しかし実質的に同種の問題として、
**`extract_tables()`が拾ったセル文字列と`extract_text()`の行順序が一致しない**
ケースが3,047セル（全体の5.5%）で発生し、value_rawをnull化した。

代表例（`biodic_6th_kanagawa_h16`, 2,755件と最多。データ密度が高い数値表に集中）:
- p.41: `'1,316 12 4813,424 15 34424 27920 9592 28869 3,4321,845 2,276'`
  → 隣接する複数列の数値が空白なしで連結され、単一セル文字列としては
  生テキスト中のどこにも同じ並びで出現しない。
- p.42: `'0.231.4'`, `'1.4 0.812.2'` → 同様に隣接列の小数値が連結。
- p.7: `'○○○○○○○○○○'` → 罫線のないチェックマーク一覧が表として誤検出された。

`suigen_hozen_final_eval` p.3（111件中の一部）は、フローチャート/年表状の図解
（「第２期５か年計画の策定」のような吹き出し・矢印付き図）を pdfplumber が
罫線ベースで表と誤認識し、視覚的に近接するテキストボックスの文字列を
「1セル」として連結してしまったケース。これは本質的にはC.表構造の問題だが、
症状（生テキストとの不一致）がOCR品質問題と同じ形で現れるため、ここに記載する。

**対処案**: pdfplumberの`explicit_vertical_lines`/`snap_tolerance`調整、または
「セル内に閾値以上の長さの数字連結がある」場合は表として採用しない
フィルタの追加。ただし今回はvalue_raw=nullで安全側に倒しており、
データの誤りとしては表出していない（読めないものを読めないと報告できている）。

## C. 表構造（結合セル・多段見出し・罫線なし表）

最大のカテゴリ。C6失敗3,907件のほぼ全て、C5失敗615件の相当数がここに分類される。

代表例:
1. `kasen_kokusei_sagami_insects`（河川水辺の国勢調査・昆虫等、C6失敗3,856件で全ドキュメント中最多）
   種目録表: `row_key='1'`（通し番号）に対し `col_key='特定外来生物等|要注意'` が
   2列分ぶら下がり重複する。原因は表の実ヘッダが3階層（例:「特定外来生物等」→
   「要注意」→ さらに細かい区分）なのに、Makerのヘッダ行検出ヒューリスティックが
   2階層までしか遡らず、区別のつかない同名col_keyを生成したため。
2. `tanzawa_shika_r6`/`tanzawa_shika_r4`（個体数調整実績表、他ページ分）
   縦書き文字（「管理捕獲」「区域」等を1文字ずつ縦に配置したラベル）が
   pdfplumber の罫線検出と噛み合わず、1つの巨大な結合セルとして
   複数の意味的に異なる行ラベルが `\n` 区切りで連結された（詳細は下記の
   個別対応を参照）。
3. `kanagawa_river_monitoring_*`（6本の結果報告書、各4〜8件と少数だが安定して発生）
   評価点（例:「川の中や水際にゴミは目につくが、我慢できる」等の水質官能評価の
   選択肢一覧）を含むテンプレート的な表で、選択肢文が罫線内で折り返されており、
   `extract_text()` 側では改行位置が異なるため literal 一致が取れない
   （B.と同種の症状としても分類しうる）。

### 個別対応（P3 Fixer, 人間によるページ画像目視確認 + 手動再構成）
最優先PDFの中で最も価値が高いとされた「ニホンジカ管理捕獲実績（年度比較）」の
サマリー表2枚（`tanzawa_shika_r6` p.4 表I-1-1、`tanzawa_shika_r4` p.3 表I-1-1）は、
上記の縦書きラベル混入によりpdfplumber抽出が完全に破綻していた
（同一row_keyが最大24件重複）ため、ページ画像を目視して手作業で
階層構造（row_key/col_key）を再構成し、`extractor="human-verified-llm@1"` として
該当テーブルのセルを置き換えた。value_rawは全て生テキストへのliteral検索で
再検証済み（0件unreadable）。結果、この2表は最終的にC1〜C6を完全に通過している
（唯一の例外は「狩猟|計(i)」列の「不明」欄=0で、その内訳2行が両方とも
「－」（非数値の空欄記号）であるため算術的に検証不能——これは内訳を
調整して合わせるのではなく、正直に「検証不能」として扱った）。

**それ以外のC.表構造の失敗（特に昆虫等11,844セル中1,928件、植物6,371セル中490件、
底生動物2,536セル中394件）は、対応の効果とコストを踏まえ、今回は手動修正の
対象外とした。** これらは分類群ごとの種チェックリスト表で、値そのもの
（●=確認/空欄=未確認）は比較的単純だが、col_keyの多段見出し
（重要種区分、特定外来生物区分、調査地点番号など）の階層検出精度に課題が残る。

## D. 定義の曖昧さ

P0で収集した語彙のうち `found_definition=1` はわずか23/408件（5.6%）。
つまり大半の区域名・区分名は、その文書中で明示的に定義されないまま使われている。
これ自体は「間違い」ではないが、複数文書を横断してデータを使う際の
リスクとして記録する。

代表例（P4注記から発見された、名称そのものが計画期間で変わった実例）:
1. `tanzawa_shika_plan5` p.43:
   「区分の「定着防止区域」の2012（平成24）〜2016（平成28）年度における
   名称は「分布拡大防止区域」。」
   → 同じ空間区分が計画期によって「監視区域」（第2次）→「分布拡大防止区域」
   （第3次）→「定着防止区域」（第4次〜第5次）と呼称変更されている。
   P6で「区域名の同一視は禁止、`areas_mapping.yaml`に人間の承認行がある場合のみ
   名寄せ」としたのはこのため。現時点で`areas_mapping.yaml`は空のまま。
2. `tanzawa_shika_r4` vs `tanzawa_shika_r6`（表I-1-1の内訳粒度そのものが変化）:
   R4版は定着防止区域(県実施分)の内訳が3区分(d,e,f)なのに対し、R6版は
   5区分(d,e,f,g,h。県森林担当部局・県自然公園担当部局・国立公園管理者・
   国有林管理者を独立行として分離)。同じ「計(d)」ラベルでも年度により
   内包範囲が異なりうる。
3. `suigen_hozen_final_eval` p.85:
   「前回、平成26(2014)年度に行ったCVMとは設問が異なっていたため、比較のため
   設問を揃えると、平成26(2014)年度は365億円/年であり、令和4(2022)年度は
   402億円/年となります。」
   → 同じ「経済評価額」指標でも算出方法(設問の有無)が版によって異なり、
   単純な数値比較ではなく「設問を揃えた再計算値」を使う必要がある。

## E. その他

- C2失敗19件: `value_raw`が`source_text`の中に見つからない軽微な不整合。
  例: `kanagawa_river_monitoring_manyual`（マニュアルPDF、数値というより
  ページ番号や図表番号がvalue_rawとして誤って拾われたケース）。
  影響は小さいが、原因は表内の参照番号（「図3-2」等）が数値として誤検出
  されたことによるMaker側のノイズ。
- `kanagawa_river_monitoring_reaflet` `reaflet2` `gyorui` `genchisheet-teisei`
  `ryouseirui` `tyourui` の6本は、pdfplumberが表を1つも検出しなかった
  （リーフレット・種チェックリスト・現地記入シートのテンプレートで、
  罫線のない自由レイアウトのため）。これは「失敗」ではなく「表がそもそもない」
  文書であり、C1〜C6の評価対象外。

## 人間の判断が必要な項目

- `data/vocab/areas_mapping.yaml` への区域名対応の記入可否
  （「定着防止区域」＝「分布拡大防止区域」＝「監視区域」の計画期をまたいだ同一視、
  および水源関連の「水源保全地域」「水源の森林エリア」「地域水源林エリア」
  「ダム集水域」の階層関係の明文化）。
- 上記A節の単位辞書パッチ（29語）の`scripts/p1_maker.py` `UNIT_TOKENS`への追加可否。
  特に「万人」「人」等の一般語に近いトークンは誤検出リスクとのトレードオフ判断が必要。
- `tanzawa_shika_r4`/`r6`の内訳粒度差（3区分 vs 5区分）を踏まえて、
  年度比較用に「計(d)」をどう対応付けるか（単純な行ラベル一致では
  不十分であることが判明したため、集計方針の決定が必要）。
- C.表構造で未対応のまま残った昆虫等・植物・底生動物の種チェックリスト表
  （failed合計 2,812セル）に対し、追加の人手/LLM修正コストをかけるかどうか。
- `suigen_hozen_final_eval`の経済評価額（CVM）は算出方法の異同を踏まえた
  「設問を揃えた再計算値」（H26:365億円/年、R4:402億円/年）を正としてよいか、
  それとも各年度の公表値をそのまま残すか。
- `kanagawa_river_monitoring_h26_sakawa_results`/`r1_sakawa_results`
  （酒匂川報告書）に「相模川では」という記述が混入している点
  （テンプレート流用起因の疑い）——原文の記述品質そのものの問題であり、
  データ構造化の範囲を超えるため、県への確認要否を判断されたい。
