# ADR-0020: 更新方式・鮮度・再ビルド運用

- 状態: 提案中 / 日付: 2026-09-06
- 関連: ADR-0001（原本と配信）, ADR-0005（版）, ADR-0011（キューブ）, ADR-0016（移行）

## 背景

ADR-0001 は「D1 は捨てて作り直せる」、ADR-0005 は「取得のたびに版が増える」と決めたが、
**どの頻度で何を作り直すか**は決めていない。データの性質は一様ではない。

| 出典の型 | 例 | 実測規模 | 更新の性質 |
|---|---|---|---|
| スナップショット全取得 | GBIF occurrences | 658,360行 | 再取得すると全件が来る |
| 追記型 | センサー時系列 | 717,839行 | 新しい期間だけ増える |
| 版が変わる台帳 | 県レッドリスト | 2,884行 | 数年に1回、版ごと差し替え |
| 年次公表 | 行政文書・統計 | cells 119,533行 | 年1回、過去は変わらない |
| ほぼ不変 | 流域界・メッシュ定義 | 4,083メッシュ | 数年〜十数年 |

スナップショット型を毎回全件保存すると、658,360行 × 版数だけ増える。
一方で「前回と同じ行」を捨てると、ADR-0005 の「版で再現できる」が崩れる。

また `wrangler d1 export` は大きいテーブルで OOM するため独自の `db:export` を使っており
（`CLAUDE.md`）、D1 への全再投入には実測で相応の時間がかかる。**全再構築を毎回やる前提の
運用は成立しない可能性が高い。**

## 決定

**更新方式をソースの性質ごとにマニフェストで宣言し（`update_mode`）、
再ビルドの単位を「全体」ではなく「ソース × 版」にする。鮮度は応答に出す。**

```yaml
update_mode: snapshot   # 再取得で全件が来る。前版との差分だけを保存する
update_mode: append     # 新しい期間だけ増える。既存行は変わらない
update_mode: revision   # 版ごと差し替え。旧版は残す
update_mode: static     # ほぼ不変。明示的に更新するまで再取得しない
```

1. **`snapshot` は差分保存にする。** 版ごとに全件を複製せず、
   「この版で追加・変更・消滅した行」を保存し、任意の版の全件は再構成できるようにする
   （行の同一性は ADR-0004 の安定 ID で判定する）。
   **これは圧縮の都合ではなく、「何が変わったか」を答えられるようにするため。**
2. **L2 の再ビルドはソース単位。** 1つの出典を再取得したら、その出典に由来する
   L2 の区画だけを作り直す（Parquet はソース × 地域でパーティションする）。
3. **L3（キューブ）の再ビルドは影響範囲で決める。** 集計定義から
   「どの入力が変わったらどのキューブが変わるか」を導き、変わるものだけ作り直す。
   全再構築は**週次のフルチェック**として別に走らせ、増分結果と一致することを検証する
   （決定性の担保。ADR-0001）。
4. **D1 への反映は差分投入を基本とする。** 全再投入は移行時と、
   フルチェックで不一致が出たときの復旧手段に位置づける。
5. **鮮度を応答に出す。** 封筒（ADR-0014）の `provenance` に各出典の `fetched_at` を含め、
   `coverage` に「このデータで最も古い取得日」を出す。
   **「いつ時点のデータか」を利用者が知らずに使える状態を作らない。**
6. **更新頻度は出典ごとにマニフェストに書き、実際の取得は人が起動する。**
   自動巡回はしない（`docs/COLLECTOR_CONTRACT.md` の外向きアクションの制約と、
   相手サイトへの負荷の両方から）。

## 影響

- **良い**: 再取得のコストが出典の規模に比例するようになる。「何が変わったか」に
  答えられる。鮮度が利用者に見える。D1 の全再投入が常態でなくなる。
- **コスト**: 差分保存と増分ビルドの実装は、全再構築より確実に複雑。
  週次フルチェックとの不一致が出たときの調査コスト。
- **リスク**: 増分ビルドのバグは「古い値が残る」形で静かに出る。
  フルチェックを省略すると気づけないので、**フルチェックは省略可能な最適化にしない**。

## 検討した代替案

- **毎回すべて作り直す**: 実装は最も単純で、決定性の担保も要らない。
  データが小さいうちは有効だが、GBIF 658k行の再取得と D1 全再投入を毎回行う運用は
  現時点でも重く、多地域化で悪化する。**ただし Phase A〜B（ADR-0016）の間はこれで良い。**
  段階的に移行する。部分的に採用。
- **差分を取らず版ごとに全件保存する**: 単純で再現性も高いが、
  スナップショット型で容量が線形に増え、「何が変わったか」も別途計算が要る。却下。
- **更新を自動巡回にする**: 鮮度は上がるが、収集規約の制約に反し、
  相手サイトへの負荷の責任を持てない。却下。
