# ADR-0015: ドメイン固有構造はコアに入れず拡張パッケージに分ける

- 状態: 提案中 / 日付: 2026-09-06
- 関連: ADR-0006（place）, ADR-0007（observation）, ADR-0012（マニフェスト）

## 背景

コアモデル（ADR-0006〜0011）は「場所 × 指標 × 時間 → 値」で表せるものを扱う。
しかし、この形に収まらない構造を持つデータが既に存在する。

**水道水の水源マップ（`docs/WATER_SOURCE_MAP.md`、8テーブル）**

```
water_utility (21)          事業体（bulk=卸 / retail=末端給水）
water_source (45)           水源。parent_id でダム→河川・支流→本流を辿る
water_facility (83)         取水堰・浄水場・配水池
water_flow_edge (134)       流れの辺。「この施設に入る水の何割がこの上流ノード由来か」
water_zone (5,089)          町丁目（割付単位）
water_zone_assignment (4,933)  町丁目→浄水場・配水池
water_zone_source_share (8,706) 派生。flow_edge を上流へ再帰的に辿った合成結果
water_source_doc (69)       根拠資料
```

これは**有向グラフ上の比率伝播**であって、観測値ではない。同じ性質のものが今後も出る
（河川ネットワークの上下流関係、食物網、行政の所管関係、施設の系統）。
これらをコアに入れると、コアが「なんでも表せるが何も保証しない」ものになる。

## 決定

**コアは10エンティティに固定し、ドメイン固有の構造は `ext_<domain>` パッケージとして分離する。
拡張はコアを参照してよいが、コアは拡張を参照しない（依存は一方向）。**

```
core/                      place, variable, observation, occurrence, taxon,
                           source, feature, document, event, caveat
ext_water/                 utility, facility, flow_edge, zone_assignment
ext_<next>/                ...
```

拡張パッケージが満たすべき条件:

1. **コアへの接続点を明示する。** `ext_water` の場合:
   - `water_zone` → `place`（`place_kind='town_block'`）に移す。町丁目はコアの空間単位
   - `water_source_doc` → `source_edition` / `document` に移す
   - `water_zone_source_share`（派生）→ 比率は拡張内に残すが、
     「町丁目 × 水源 → 比率」として `observation_agg` にも射影できる
   - 残る `utility` / `facility` / `flow_edge` が拡張の本体
2. **拡張だけを外しても、コアと他の拡張が壊れない。**
3. **拡張はマニフェスト（ADR-0012）とコードリストの枠組みを共有する。**
   独自の取り込み経路を作らない。
4. **拡張の API/MCP はコアのツールに寄せる。** どうしても表せない問い
   （「この蛇口の水はどこから来たか」）にだけ専用ツールを足し、
   その理由を ADR に残す。
5. **拡張を作る判断基準**: コアの `observation` / `feature` / `place_relation` で
   3回試して表せなかったものだけを拡張にする。安易に作らない。

## 影響

- **良い**: コアが痩せたまま保たれ、新ドメイン（食物網、施設系統、所管関係）を
  足しても既存が壊れない。「水道は特殊」という事実がモデル上に見える。
  拡張ごとに担当を分けられる（シビックテック的な分業に向く）。
- **コスト**: どこまでがコアでどこからが拡張かの線引きに判断が要り、
  議論のたびにコストが発生する。拡張が増えると全体像の把握が難しくなる。
- **注意**: `place_relation` に `flows_to` を入れるか（コア）、`ext_water.flow_edge` に
  留めるか（拡張）は境界事例。**河川の上下流はコア**（多くのドメインが使う）、
  **水道網の配分比率は拡張**（水道固有）と切る。この線引き自体をこの ADR で決めておく。

## 検討した代替案

- **すべてコアに入れる**: 統一感はあるが、コアが肥大化し、
  「コアを実装すれば最低限動く」という保証が失われる。他地域が導入する際の敷居が上がる。却下。
- **拡張ごとに独立したデータベース/リポジトリにする**: 分離は最も強いが、
  place / source / caveat の共有ができず、拡張が孤立する。却下。
- **拡張を作らず、表せないものは扱わない**: コアは綺麗に保てるが、
  既に存在する水道マップ（`docs/WATER_SOURCE_MAP.md` の成果）を捨てることになる。却下。
