# ADR-0029: v1 の撤去と検証の引き継ぎ

- 状態: 提案中（オーナー承認待ち） / 日付: 2026-09-26
- 関連: ADR-0011（キューブ）, ADR-0016（移行計画・受け入れ基準）, ADR-0021（キューブの粒度）,
  ADR-0027（テスト・検証戦略の4層。本 ADR が層2・層3を置き換える）,
  ADR-0030（D1 の配信スキーマ。本 ADR と対で読む）,
  Issue #48（親 #27、対象 #28・#41）, [docs/plans/V2_SERVING.md](../plans/V2_SERVING.md)（移行計画本体）

## 背景

[ADR-0027](0027-test-and-verification-strategy.md) の層2（縮小サンプル突合）・層3（全量の
実行証明）は、どちらも「**v1（`web/scripts/build-derived.mjs` が書く派生33表）が正解**で、
v2（`scripts/b03`〜`b12` のパイプライン）がそれを再現できているか」を検証の軸にしている。
この軸は [ADR-0016](0016-migration-plan.md) Phase B の受け入れ基準（`imputation='zero'`
で v1 の派生33表を再現できること）をそのまま反映したもので、「移行の誤りと意図的な変更を
分離する」ために意図的に採用した設計だった。

`docs/plans/V2_SERVING.md`（Issue #48、オーナー決定 2026-09-26）は、この先で v1 の派生33表
と旧 JS パイプラインそのものを撤去し、画面・API・AI ツールがキューブ
（`observation_agg`/`occurrence_agg`）とレジストリを直接読む形に切り替える。**v1 が無くなれば
「v1 と一致しているか」という軸そのものが成立しなくなる**——層2・層3はどちらも比較対象を
失う。一方で、v1 という正解を失ったあとも「画面・AI が実際に投げる問い合わせが、意図せず
壊れていないか」を検証する手段は要る。本 ADR は、ADR-0027 が既に確立した「層に分けて保証
範囲を分担する」という考え方を保ったまま、層2・層3の**比較対象を v1 から「凍結した過去の
自分自身」に付け替える**設計を決める。

## 決定

### 引き継がないもの・引き継ぐもの

| ADR-0027 の層 | v1 撤去前 | v1 撤去後（本 ADR） |
|---|---|---|
| 層1（フィクスチャテスト） | ハーネスのロジックを検証 | **変わらない**。v1 の有無に依存しない |
| 層2（縮小サンプル突合） | v1/v2 双方を構築し33表を突合 | **凍結スナップショット**（下記）に置き換え |
| 層3（全量の実行証明） | v1/v2 双方を手元で回し33表を突合、証明を記録 | **`serving_fingerprint.json`**（下記）に置き換え |
| 層4（段階間の指紋） | v2 パイプライン内部の整合性 | **変わらない**。v1 の有無に依存しない |
| （新設）差分カウント | — | **serving-diff**（下記）。PR-1〜PR-4 の移行期間限定 |

### 層2の後継: 凍結スナップショット（`web/serving_queries.yaml` → `data/sample/serving_snapshot.json`）

- 画面・AI アシスタントが実際に投げる問い合わせ（`web/src/lib/cube/` の呼び出しパターン。
  `variable_id`・`scope`・`grain`・`imputation` 等の組を列挙したもの）を
  `web/serving_queries.yaml`（新設予定）に宣言する。
- 縮小サンプル（`data/sample/`、`scripts/s01_build_sample.py`）から v2 を構築し、
  問い合わせ層（`web/src/lib/cube/`）に通した結果を `data/sample/serving_snapshot.json`
  （新設予定）としてコミットする。
- CI の `sample-gate` ジョブは「v2 構築 → `serving_queries.yaml` を全件実行 →
  スナップショットとの `git diff --exit-code`」に変わる。
- **免除リスト（`expected_diffs.yaml` 相当）は持たない。** ADR-0027 層2が持っていた
  `declaration_counts.yaml`（サンプルの件数を宣言する仕組み）とは役割が違う——あちらは
  「サンプルが原本の何を代表しているか」の宣言で、こちらは「今の出力そのもの」を固定する
  仕組みなので、値のずれを免除する仕組みを重ねる必要が無い。**スナップショットの更新
  そのものが「この差分を意図して受け入れる」という宣言になる**（Git の diff がレビュー
  対象そのものになる）。
- **スナップショット更新 PR には serving-diff の表（下記）を必須にする**——ADR-0027 の
  層2が「原本のある手元でしか作れない証明の申告制」に頼っていたのと同じ弱点をここでも
  持つ（スナップショットは書き換えれば通る値でもある）。単体では防げないので、運用規約
  として明文化する（Issue #48 危険16件 #16 が指摘した「黙って更新させない」）。

### 層3の後継: 全量の実行証明（`reports/serving_fingerprint.json`）

- `scripts/b00_run_full_gate.py`（既存）は、r01→b03…b13 → キューブの自己不変条件（下記）
  → `serving_queries.yaml` を**全量**で実行し、`reports/serving_fingerprint.json`
  （新設予定。問い合わせごとの行数・値の和・hash、前回との差分の分類）を書く形に付け替える。
- CI の `full-gate-proof-check` ジョブは、証明が記録するパイプラインのパスの
  git tree/blob ハッシュを HEAD で計算し直し、1つでも食い違えば「証明が古い」として落ちる
  ——この仕組み自体は ADR-0027 層3から変えない。**保証しないこと**も同様に引き継ぐ:
  証明が本物であること（手で書ける値でもある）・CI 自身が全量を再現すること
  （原本が CI に無いため）・原本のスナップショットが変わっていないこと。

### キューブの自己不変条件を先に移してから射影を消す

v1 互換の射影（`scripts/b05_project_v1.py`/`b08_project_occurrence_v1.py`/
`b09_build_occurrence_place.py`）には、キューブそのものの正しさを守る検証が同居している
（`verify_hourly_daily_rollup`・`assert_alias_is_function`/`assert_unit_raw_is_function`
〔`scripts/migrate/v1_projection_checks.py`〕・流域の保存則〔ADR-0026 D2〕）。これらは
「v1 と一致するか」ではなく「キューブが自己無矛盾か」を見ているので、**射影を撤去する
（`docs/plans/V2_SERVING.md` PR-5）前に b04/b07/b09（キューブの構築側）へ移す**
（`docs/plans/V2_SERVING.md` §4-1）。加えて、無作為抽出したセルを `observation` から
独立に再計算して一致を見る検査を b04 に新設する——これは v1 にも無かった検証で、
v1 という「もう一つの経路」を失うぶんを補う。

### 差分カウントの道具（`web/scripts/serving-diff.mts`、移行期間限定）

`docs/plans/V2_SERVING.md` PR-1〜PR-4（値が動く切り替え）の受け入れに使う、v1 撤去
（PR-5）までの間だけ意味を持つ道具。同じ `serving_queries.yaml` を、v1 経路（今の
`web/src/lib/queries.ts`）と v2 経路（`web/src/lib/cube/`）の両方に、旧表と新表が
同居するローカル D1 上で流し、問い合わせごとの差を `reports/serving_switch_diff.md`
（新設予定）に書く。

`imputation=zero` で流したとき、差分が次の**既知の系統だけ**に分類されれば合格
（それ以外の差分が出たら問い合わせ層のバグ）:

1. 宣言済み差分20件（v1 の「未満」判定バグ、既存 `scripts/reconcile/expected_diffs.yaml`
   が記録している8表分）
2. 日割り（`sensor_daily` 9,424行・`rain_daily` 549行、ADR-0024 決定2の時刻ラベル日割り）
3. 流域のメモ化の癖（1,091キー、ADR-0026 D2）
4. Sirosporium（学名解決の既知の個別差分）
5. 合成データの除外（`docs/plans/V2_SERVING.md` §2-3）
6. 雨量の `/10`（`docs/plans/V2_SERVING.md` §6 決定6。v1 の単位不明の推測換算を撤去する
   意図的な変更）

PR-5 で v1（`web/src/lib/queries.ts` が読む派生33表）を撤去したあとは、serving-diff は
比較先の v1 経路を失う。**PR-5 以降は動かさない**——削除はしないが（過去の切り替え差分の
記録として残る）、CI では呼ばない。

## 根拠（却下した代替案）

- **層2・層3を単純に廃止し、層1・層4だけで済ませる**: 却下。層1（フィクスチャ）は実データの
  癖を拾わず、層4（段階間の指紋）は v2 内部の整合性しか見ない——「画面・AI が実際に投げる
  問い合わせの出力が変わっていないか」を保証する層が無くなる。ADR-0027 の「どの層も他の層の
  代わりにはならない」という原則をそのまま引き継ぐ。
- **v1 を検証専用に一部残す（コードは消すがゲートだけ動かす）**: 却下。
  `docs/plans/V2_SERVING.md` のオーナー決定「v1 のレガシーは一切残さない」に反する。
  serving-diff を PR-1〜PR-4 の**移行期間限定**の道具にすることで、同じ目的
  （切り替え時の差分を機械的に説明できる状態にする）を「v1 を永続的に残さず」達成する。
- **スナップショットに免除リストを持たせる**: 却下（上記「層2の後継」参照）。ADR-0027 層2の
  免除の仕組み（`declaration_counts.yaml`）とスナップショットの役割は異なり、免除を重ねると
  「スナップショットを更新したのか、免除で通したのか」が曖昧になる。

## 影響

- **良い**: v1 という比較対象を失っても、「画面・AI の出力が意図せず壊れていないか」を
  引き続き機械的に検証できる。検証の正が「過去の v1」から「宣言された問い合わせ集合
  （`serving_queries.yaml`）に対する過去の自分自身」に移り、**新しい問い合わせを足すたびに
  検証範囲が広がる**（v1 には無かった性質）。
- **コスト**: `serving_queries.yaml` の宣言漏れは検証の穴になる——v1 比較（ADR-0027 層2）は
  33表という有限の対象を機械的に列挙できたが、本 ADR の凍結スナップショットは「画面・AI が
  実際に投げる問い合わせ」を人が宣言する必要があり、宣言し忘れた問い合わせは守られない。
- **リスク**: スナップショットの更新は「差分を正として受け入れる」操作であり、
  レビュー抜きで通せば意図しない回帰をスナップショットごと固定してしまう。運用ルール
  （更新 PR には serving-diff の表を必須にする）で緩和するが、ツールだけでは強制できない
  （Issue #48 危険16件 #16）。

## 検討した代替案

- **層3（全量の実行証明）を廃止し、層2（サンプル）だけにする**: 却下。ADR-0027 が既に
  「層2だけでは、サンプルに無い癖を原理的に検出できない」と結論している。この制約は
  比較対象が v1 か凍結スナップショットかに関わらず変わらない。
- **serving-diff を PR-5 後も CI に残し、v1 のコードだけをアーカイブブランチに退避して
  参照可能にする**: 却下。「v1 のレガシーは一切残さない」というオーナー決定（§背景）と
  「アーキテクチャ的に一番きれいな状態にする」という目的に反する。過去の
  `reports/serving_switch_diff.md` という記録で十分とする。
