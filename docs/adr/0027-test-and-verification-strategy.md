# ADR-0027: テスト・検証戦略は4層に分け、層ごとに保証範囲を分担する

- 状態: 承認済 / 日付: 2026-09-25
- 関連: ADR-0016（移行計画・受け入れ基準）, ADR-0021（キューブの粒度）,
  Issue #29（突合ゲートの継続実行）, Issue #37（段階間の指紋）

**2026-09-26 追記（Issue #48、ADR-0029提案）**: v1 の派生33表を撤去すると、層2・層3が
比較対象にしている「v1」そのものが無くなる。層2・層3の後継設計は
[ADR-0029](0029-v1-removal-and-verification-handoff.md)（提案中）に書く。本文・層1・層4は
このADRのまま変えない。

## 背景

ADR-0016 の受け入れ基準（`imputation='zero'` の系列で v1 の派生33表を再現
できること）を確かめる `scripts/b02_run_all_gates.py` は、原本
（`data/db/ryuiki.sqlite` 828MB・`cells.sqlite` 42MB・`derived.sqlite`
448MB、合計 14GB 前後）を必要とする。原本は「100MB 超のため別配布」で
git に置けず、CI（GitHub Actions）には無い。Issue #27（親Issue）の
README「未着手」表は「テスト・検証戦略」を独立の論点として残していたが、
これは Issue #29 で実装した仕組み（縮小サンプル＋実行証明）と表裏一体
であり、既に本 ADR として書けるだけの実装・検証が揃っている。

## 決定

このリポジトリの「v1 と一致しているか／パイプラインが正しく動くか」の
検証は、**保証範囲が異なる4層**に分ける。どの層も他の層の代わりにはならない
——重ねることで初めて「原本が CI に無い」という制約の中で実用的な検証に
なる。

### 層1: フィクスチャテスト（`scripts/tests/`、pytest）

- **何を保証するか**: ハーネス自体（`b01`/`b02`/`b03`〜`b12`/
  `scripts/migrate/`/`scripts/reconcile/`/`scripts/registry/`）のロジックが
  正しいこと。自前の小さな sqlite・YAML だけで、決定論（2回実行のバイト
  一致）・値の食い違いの検出・行の追加削除の検出・宣言的キーの優先・
  検証をすり抜けない設計（腐った宣言済み差分を検出する等）を確認する。
- **何を保証しないか**: 実データに対する挙動。フィクスチャは「起こりうる
  形」を人が選んで作るので、実データにしか無い癖（表記ゆれ・境界値・
  想定していなかった組み合わせ）は原理的に拾えない。
- 実行: CI の `web`/`reconcile` ジョブ、原本を必要としない（既存）。

### 層2: 縮小サンプルでの突合（`data/sample/`、CI の `sample-gate` ジョブ）

- **何を保証するか**: 原本から機械的に切り出した縮小サンプル
  （`scripts/s01_build_sample.py`。`data/sample/coverage.yaml` の宣言に
  基づく選択＋閉包）に対して、v1（`build-derived.mjs` 等）と v2（`r01`・
  `b03`〜`b12`）を実際にゼロから構築し、33表を
  `scripts/b02_run_all_gates.py` で突き合わせる。**実データの癖の代表例
  （定量下限の各表記・厚木の4桁測定日・地盤沈下の版重複・負の値・
  センサーの時刻帯・occurrence の12形・流域外の座標・年またぎ区間・
  除外種と外来種・レッドリスト種・全 source_id）を毎回の CI 実行で
  実際に踏む**——層1のフィクスチャでは拾えない「実データでしか起きない
  組み合わせ」を、原本無しで再現する。
- **何を保証しないか**: サンプルに無い行・癖。サンプルの件数の宣言
  （`declaration_counts.yaml`）が原本の件数を語ること。HEAD の全量で
  v1 と v2 が一致すること。詳細は
  [docs/plans/PHASE_B_RECONCILIATION.md](../plans/PHASE_B_RECONCILIATION.md)
  §5.1。
- 実行: CI の `sample-gate` ジョブ、原本を必要としない（新設）。

### 層3: 全量の実行証明（`reports/full_gate_proof.json`、CI の
`full-gate-proof-check` ジョブ）

- **何を保証するか**: 原本のある手元で `scripts/b00_run_full_gate.py` を
  ゼロから回し、33表が全数「一致」または「宣言済み差分のみ」（不一致・
  対象外が無い）になったときだけ証明を書く。CI は、証明が記録する
  パイプラインのパスの git tree/blob ハッシュを HEAD で計算し直し、
  1つでも食い違えば「証明が古い」として落ちる。
- **何を保証しないか**: 証明が本物であること（手で書ける値でもある）。
  CI 自身が全量を再現すること（原本が CI に無いため、今回も引き続き
  できない）。原本のスナップショットが変わっていないこと（sha256 の
  記録以上には確かめられない）。詳細は同ドキュメント §5.2。
- 実行: 層3-a（証明を取る）は手元でのみ、層3-b（証明の鮮度検査）は
  CI の `full-gate-proof-check` ジョブ、原本を必要としない（新設）。

### 層4: 段階間の指紋（Issue #37 #1。`scripts/migrate/common.py` の
`record_stage_fingerprint`/`assert_stage_fingerprint_fresh`/`track_reads`）

- **何を保証するか**: パイプラインの**各実行時**に、ある段の出力が
  「今の上流の出力から作られた状態」であることと、「実際に読んだ表を
  検証し忘れていないか」を機械的に確認する。例えば `b05` は
  `observation_agg` が古い `observation` から作られたままなら実行時点で
  止まる（系譜を再帰的に遡って確認する）。
- **何を保証しないか**: v1 との一致。この層は v2 パイプライン**内部**の
  整合性（「正しい入力から作ったか」）だけを見る——「その値が v1 と
  一致するか」は層2・層3の役目。
- 実行: 手元・CI どちらでもパイプラインを実行するたびに自動的に働く
  （層2・層3のどちらの実行でも通っている）。原本を必要としない
  （ロジック自体はどのデータに対しても動く）。

## 表: 層と保証範囲

| 層 | 対象 | 原本が要るか | v1 との一致を見るか | 実データの癖を踏むか | 実行場所 |
|---|---|---|---|---|---|
| 1. フィクスチャテスト | ハーネスのロジック | 不要 | いいえ（フィクスチャのみ） | いいえ | CI（毎回） |
| 2. 縮小サンプル突合 | v1/v2 パイプライン全体 | 不要（サンプルのみ） | はい（サンプル規模） | はい（サンプルに含めた範囲） | CI（毎回） |
| 3. 全量の実行証明 | v1/v2 パイプライン全体 | 証明を取るときだけ要る | はい（全量。ただし申告） | はい（全量） | 手元（証明を取るとき）＋CI（鮮度検査は毎回） |
| 4. 段階間の指紋 | v2 パイプラインの内部整合性 | 不要 | いいえ | 該当なし | 実行のたび自動 |

## 根拠（却下した代替案）

- **層2だけで十分としない**: サンプルは有限であり、原理的に「サンプルに
  無い癖」を検出できない。全量の合否を語れるのは層3だけ（ただし層3は
  CI が真偽を確かめられない申告に留まる——これも正直に書く）。
- **層3（原本必須のセルフホストランナー）だけで済ませない**: Issue #29 の
  親検討（#27 の候補2「セルフホストランナーに原本を置く」）は運用の手当て
  （原本の配置・セキュリティ・可用性）が要ると判断し採らなかった
  （`docs/plans/PHASE_B_RECONCILIATION.md` の元 Issue 本文参照）。
- **層4を層2/3の代わりにしない**: 段階間の指紋は「今の上流から作ったか」
  という**v2内部**の整合性であり、「v1と一致するか」を一切見ない。別の
  軸の検証であり、統合しない。
