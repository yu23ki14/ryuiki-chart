# ADR-0002: 多地域前提でモデリングし、地域固有語彙をコードリストの拡張として扱う

- 状態: 提案中 / 日付: 2026-09-06
- 関連: ADR-0004（識別子）, ADR-0006（place）, ADR-0010（variable）

## 背景

`app_description.md` の舞台は奄美・秋名（龍郷町）だが、本デモの対象は神奈川県全域である。
これは FR-5.4「地域固有語彙のハードコード禁止」に沿った意図的な選択で、
**同じモデルが2地域で成立することを確かめるための設計上のテスト**でもある。

しかし現行モデルには地域の概念が無く、地域固有の前提が随所に埋まっている。

- `sites.zone`（Ridge to Reef 1〜5）は標高と海岸距離による**操作的定義**であり、
  公式区分ではない（`docs/ZONE_DEFINITION.md`）。閾値（800m / 400m / 100m / 海岸2km）は
  神奈川の地形に合わせたもので、奄美にそのまま当てはまらない。
- `watershed_id` は国土数値情報の流域界コード（例 `83032-0024`）で、これも日本の特定データ由来。
- 指標名・単位・レッドリストのカテゴリ体系は自治体ごとに版が違う。

## 決定

**`region` を第一級の次元として導入し、地域固有の値はコードリストの拡張として表現する。**

1. すべてのコアエンティティが `region_id`（例 `jp-14`＝神奈川県, `jp-46-tatsugo`）を持つ。
   Parquet のパーティションキーにも使う（`core/observation/region_id=jp-14/*.parquet`）。
2. **分岐（if 地域）を書かない。** 地域差はデータで表す:
   - `zone` のような操作的分類は `place_kind='zone'` の place として地域ごとに定義し、
     **定義そのもの（閾値・出典・作成日）を place のメタデータに持たせる**。
   - 指標の別名・単位・レッドリストのカテゴリ体系は語彙テーブルの行として地域ごとに足す。
3. コードリストは**共通部分＋地域拡張**の2層。共通に無い語を地域が足せるが、共通語の
   意味を地域が上書きすることは禁止する。
4. 地域をまたぐ比較は「共通語彙に解決できた指標のみ」で行い、解決できないものは
   応答で明示する（ADR-0014 の `coverage`）。

## 影響

- **良い**: 龍郷を足すときにスキーマ変更もコード分岐も要らない。`zone` の定義が
  データとして可視になり、「これは公式区分ではない」という注記がモデル上に載る。
- **コスト**: 全テーブルに `region_id` が付き、クエリと結合が1列ぶん増える。
  「地域をまたぐ集計」の意味（例: 神奈川と奄美の BOD 平均）を毎回考える必要が出る。
- **リスク**: 地域拡張の語彙が増えすぎると共通語彙が痩せる。共通に昇格させる基準を
  ADR-0010 で決めておく必要がある。

## 検討した代替案

- **神奈川デモに閉じる**: 最短だが、地域次元は後から入れるのが最も難しい種類の変更
  （全ファクトの再構築と全 ID の付け替えを伴う）。目的（他地域への横展開、Y3 の
  「5地域で導入決定」）に反する。却下。
- **地域ごとに別データベース**: 分離は簡単だが、地域横断の問い（他地域と比べてどうか）に
  答えられず、語彙の統制も効かない。却下。
- **さらに抽象化して「流域」以外のドメインも視野に入れる**: 汎用性は最大だが、
  当てはめの手間が増え、Y1〜Y3 のスコープに対して過剰。ADR-0015 の拡張パッケージ方式で
  必要になった時点で対応する。見送り。

## 実務手順

新しいエリアを実際に足す手順（エリア定数の調べ方・スキーマへの `region_id` 追加・
収集スクリプトの差し替え）は `docs/add_area.md` にまとめてある。本 ADR の決定を覆すものではない。
