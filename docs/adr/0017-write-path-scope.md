# ADR-0017: 本 ADR 群は読み取り基盤に限る。書き込み経路と可変データの所在を分ける

- 状態: 提案中 / 日付: 2026-09-06
- 関連: ADR-0001（D1 は捨てられる）, ADR-0005（版）

## 背景

`app_description.md`（要求定義書 v0.1）の主役は**現場での入力**である。

- U1 現地測定者は圏外・不安定が常態の環境でスマホから入力する（FR-1、オフライン同期）
- 品質段階（暫定 → 検証済 → 公開済）の遷移を記録する（FR-2.1、`quality_transitions` 3,372行）
- 介入記録・意思決定記録を人が書く（`interventions` 20行、`decisions` 14行）
- NFR-6 として「上書き削除の禁止」がある

一方、ADR-0001 は「D1 はいつ捨てて作り直してもよい配信キャッシュ」と決めた。
**利用者が入力したデータを D1 に置くと、この2つが正面衝突する**（作り直したら消える）。

現在のデモではこの矛盾は顕在化していない。`quality_transitions` も `interventions` も
`decisions` も全件が合成データで、パイプラインが生成したものだからである。
しかし本番では人が書く。**ADR 群がこの点に沈黙したままだと、実装時に事故になる。**

## 決定

**ADR-0001〜0016 は「収集済みデータを正規化して読ませる基盤」に限る。
人が書き込むデータは別系統として扱い、本 ADR 群の対象外であることを明示する。**

境界:

| 区分 | 性質 | 置き場 | 本 ADR 群の対象 |
|---|---|---|---|
| 外部から収集したデータ | 不変・再取得可能 | L0→L2 Parquet → D1 | **対象** |
| 集計・派生 | 再構築可能 | L3 → D1 | **対象** |
| 現場入力・品質遷移・介入・意思決定 | **可変・再構築不能** | 別ストア（未定） | **対象外** |
| 語彙・マニフェスト・集計定義 | 可変だが Git 管理 | リポジトリ | 対象（レビュー経由） |

原則:

1. **再構築不能なデータを「捨てられるストア」に置かない。** 現場入力を D1 に置くなら、
   D1 は捨てられなくなる。どちらかを選ぶ必要があり、本 ADR では**分ける**を選ぶ。
2. **書き込み系のデータも、読み取り基盤には L1 相当のソースとして入ってくる。**
   現場入力は「1つの出典」として `source_edition` を持ち、他の収集データと同じ経路で
   L2 に入る。**書き込みストアと読み取り基盤を直結しない。**
3. 書き込み経路（オフライン同期、競合解決、認証、上書き削除の禁止）は**別の ADR 群**で決める。
   この境界を先に引いておかないと、両者の要求が混ざって設計が破綻する。
4. デモに含まれる合成の可変データ（`quality_transitions` / `interventions` / `decisions`）は
   当面 L2 の一部として扱い、**合成である旨を caveat で明示する**（ADR-0013）。

## 影響

- **良い**: 「D1 は捨てられる」が例外なく成立する。読み取り基盤の設計が単純に保たれる。
  公開パイプラインとしての切り出し（他組織が読み取り基盤だけ使う）が可能になる。
- **コスト**: 書き込み系のストアと同期の設計が別途必要になる。
  現場入力が読み取り基盤に反映されるまでのラグが生じる（ADR-0020 の鮮度と関わる）。
- **リスク**: 「対象外」と書いたまま誰も設計しないと、要求定義の主役が実装されない。
  **本 ADR は先送りの宣言ではなく、境界の宣言である**ことを明記する。

## 検討した代替案

- **書き込みも同じ基盤に含める**: 一体感はあるが、ADR-0001 と矛盾し、
  設計の複雑さが跳ね上がる（オフライン同期・競合解決・認証が読み取り側に染み出す）。却下。
- **D1 を「捨てられない」に変更する**: 書き込みを素直に扱えるが、
  Parquet 原本・決定的再生成という ADR-0001 の利点を失う。却下。
- **沈黙したまま進める（現状）**: 実装時に必ず衝突する。却下。
