# ADR-0016: 移行は4段階に分け、v1 の数値を再現できることを受け入れ基準にする

- 状態: 提案中 / 日付: 2026-09-06
- 関連: ADR-0004, 0006, 0008, 0009, 0010, 0011

## 背景

ADR-0004〜0015 を一度に適用すると、次がすべて同時に起きる。

- 全 ID の付け替え（ADR-0004）
- 日付列の3列展開・323,164行（ADR-0008）
- 検閲値の `0` → `NULL` 化により**既存の全グラフの数値が変わる**（ADR-0009）
  実測: `web/scripts/build-derived.mjs` は `AVG(value)` で検閲行の 0 を平均に含めており、
  現行の平均は下方に偏っている。修正すると全水質グラフが上に動く。
- 指標58種＋センサー datastream 群＋Tier 1 の人手棚卸し（ADR-0010）
- `sites` に無い地点（センサー65地点・測定7,846行）の place 登録と点→place 解決（ADR-0006）

これを一括で行うと、どこで壊れたかが分からなくなる。また「数値が変わった」ことと
「移行を間違えた」ことを区別する手段が無い。

## 決定

**4段階に分け、各段階に受け入れ基準を置く。v2 が v1 の数値を再現できることを
先に確かめてから、意図的な変更を入れる。**

### Phase A — レジストリの並走（データを動かさない）

`variable` / `place` / `taxon` / `caveat` / `unit` のレジストリを、v1 のテーブルと
**並走**して作る。v1 のファクトは触らない。レジストリを v1 の値に対応付ける
（`variable_alias` が `measurements.variable` の58種を解決できる、など）。

- 受け入れ基準: v1 の全ファクトの `variable` / `site_id` / 座標が
  レジストリで解決できる（解決率と未解決一覧をレポート）。
- 実装計画: [docs/plans/PHASE_A.md](../plans/PHASE_A.md)
- **先に効かせる先は AI アシスタントと MCP**。`domain.ts` の知識をレジストリから引くようにする。
  ここだけで「MCP が誤読する」問題の大半が解ける。

### Phase B — ファクトとキューブ（数値の再現を確かめる）

`observation` / `occurrence` を作り、キューブを生成する。

- **受け入れ基準: `imputation='zero'` の系列で v1 の派生テーブルの値が再現できること。**
  これは「v1 が正しい」という意味ではなく、**移行の誤りと意図的な変更を分離する**ため。
  再現を確認したうえで `imputation` を `zero`/`lod` 併記に切り替える（ADR-0009）。
- 行数・件数の突合レポートを CI の成果物にする（v1 テーブル別の行数差・値差の分布）。
- この段階で `place_id=NULL`（解決できない座標）の件数が確定する。

### Phase C — ID と版

ADR-0004 の ID 規約と ADR-0005 の `source_edition` を適用する。旧 ID → 新 ID の
対応表を残す。公開 ID の発行はここから。

- 受け入れ基準: 旧 ID から新 ID が一意に引ける。`superseded_by` で
  `gbif_kanagawa` → `gbif_kanagawa_occurrences` の関係が表現できている。

### Phase D — マニフェストと公開

ADR-0012 のマニフェストへ移行し、`dist/` の生成と MCP を公開する。

- 受け入れ基準: 新規ソース1件を、共通ライブラリに手を入れずに追加できる。

## 影響

- **良い**: 「数値が変わった」ときに、それが意図的か誤りかを判別できる。
  Phase A だけでも MCP の誤読問題に効くので、価値が早く出る。
- **コスト**: 並走期間中は v1 と v2 の両方を維持する必要がある。
  突合レポートの実装コスト。
- **注意**: Phase B で v1 が再現できない箇所が出たら、**それは v1 のバグの発見**でもある。
  再現できない理由を1件ずつ記録する（黙って v2 の値を正とみなさない）。

## 検討した代替案

- **一括で切り替える**: 期間は短いが、上記の判別ができない。却下。
- **v1 を残したまま v2 を別サービスとして作る**: リスクは低いが、
  二重メンテが恒久化し、`domain.ts` の知識が2箇所に増える。却下。
- **Phase B の受け入れ基準を「新しい値が正しいこと」にする**: 理想だが、
  正しさを独立に検証する手段（第三者データ）が無い項目が多い。再現性で代用する。
