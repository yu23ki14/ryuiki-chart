# ADR-0003: 外部標準（DwC-A / SensorThings / DCAT）は境界のアダプタで満たす

- 状態: 提案中 / 日付: 2026-09-06
- 関連: ADR-0007（observation）, ADR-0014（インターフェース）

## 背景

本基盤は3つの外部標準に関わる。

| 標準 | 現状 | 要件の出どころ |
|---|---|---|
| DwC-A（Event Core + Occurrence + eMoF） | `scripts/x01_dwca.py` で出力済み | GBIF 公開（FR-4.1 / FR-4.2） |
| OGC SensorThings | `sensor_timeseries` が既にほぼ同型（Datastream / Observation / phenomenonTime / result） | センサー系の相互運用 |
| DCAT / Frictionless | 未対応。`source_registry` が近い | 公開カタログ・自治体オープンデータ連携 |

「どの標準に準拠するか」を検討した結果、**3つとも満たしつつ、準拠は最小限にする**という
一見矛盾する要求になった。これを設計としてどう解くかを決める必要がある。

## 決定

**3標準は L3 の先の「アダプタ層」の責務とし、コアモデル（L2）の語彙には持ち込まない。
射影は片方向（コア → 標準）のみで、逆向きの変換は行わない。**

```
L2 canonical  ──┬─→ DwC-A adapter            → GBIF 公開（zip）
                ├─→ SensorThings exporter    → STA 形の JSON エクスポート（下記）
                └─→ DCAT/Frictionless adapter → カタログ・データパッケージ記述子
```

**SensorThings は「STA 形の JSON を書き出す」に留め、OData 風のクエリ API は実装しない。**
STA 準拠の API サーバは `$expand` / `$filter` を含む仕様であり、静的キューブ配信
（ADR-0001）の上に載せる規模ではない。相互運用の実利は Datastream/Observation の
**形**にあり、クエリ言語にはない。この解釈を FR-4.3 に対する回答として記録する。

- コアの列名は自前の語彙（`variable_id`, `place_id`, `period_start`, `censoring` …）を使う。
  `basisOfRecord` や `phenomenonTime` をコアの列名にしない。
- 各アダプタは**マッピング表**を1つ持ち、それがコアと標準の唯一の接点になる。
  標準の版が上がったらアダプタとマッピング表だけを直す。
- 標準に載らない情報（検閲区分、品質段階、注意事項、地域）は**落とさずコアに残す**。
  アダプタは落とすことを明示的に記録する（何を落としたかを出力に含める）。
- 外部データを取り込む際も、DwC/STA の語彙のままコアに入れない。L1→L2 のマニフェスト
  （ADR-0012）でコア語彙に解決する。

## 根拠

- コアに DwC の語彙を埋めると、非生物データ（水質323k行・センサー718k行・土地利用・
  水道網）が「生物レコードの語彙で説明される」歪みが出る。生物は `occurrence` 823k行で
  確かに大きいが、全体の過半ではない。
- 多地域展開（ADR-0002）では地域固有の語（`zone`、県レッドリストのカテゴリ）が必ず出る。
  これらは3標準のどれにも席がない。標準をコアにすると置き場を失う。
- 逆に、標準を境界に置けば「1つのコアから3つとも出す」ことが素直に成立する。

## 影響

- **良い**: 標準の版差・仕様変更の影響がアダプタに閉じる。標準に無い概念を諦めずに済む。
  「最小限の準拠」と「3標準対応」が両立する。
- **コスト**: アダプタ3本ぶんのコードとマッピング表の維持。コア列名と標準列名の対応を
  常に説明する必要がある（ドキュメント負債）。
- **注意**: DwC-A の出力は現在ライセンス区分で `noncommercial`/`unknown` を除外している。
  この判断は**アダプタ側のポリシー**として明示的に持つ（ADR-0005）。

## 検討した代替案

- **DwC をコアの語彙にする**: 生物データの変換が不要になるが、上記の歪みが出る。却下。
- **標準対応をやめて独自形式のみ公開**: 実装は最小だが、GBIF 公開は要求定義の明示要件
  （FR-4.1）であり選べない。却下。
- **標準ごとにデータの持ち方を分ける**: 現行がこれに近い（`organism_records` は DwC 風、
  `sensor_timeseries` は STA 風、`measurements` は独自）。結果として同じ物理量が
  3つの表に別語彙で入っている（README §1(c)）。この状態の解消が本 ADR の動機。却下。
