#### B-1. 区域名の名寄せ — 【判断済み】シカ管理区分のみ承認、水源系は否認

`data/vocab/areas_mapping.yaml` に承認行を記入した。**このファイルを読むコードは存在しない**ため、
記入自体がデータを書き換えることはない（将来の名寄せを認可する宣言）。行を消せば元に戻る。

**(a) シカ管理区分 — 承認した**

「定着防止区域」＝「分布拡大防止区域」＝「監視区域」を、**名称の系譜としての同一視**に限って承認。
根拠は我々の推測ではなく、県の原資料そのものが同一性を明記していること:

> （※第3次計画中は「分布拡大防止区域」、第2次計画中は「監視区域」）
> — `cells.sqlite` notes.`tanzawa_shika_plan5_n001`（tanzawa_shika_plan5 p.2）

> 区分の「定着防止区域」の2012（平成24）〜2016（平成28）年度における名称は「分布拡大防止区域」。
> — 同 notes.`tanzawa_shika_plan5_n004`（p.43）

さらに `tanzawa_shika_r4`/`r6` の表の行見出しが
`定着防止区域合計(H28まで分布拡大防止区域)` と**県自身がインラインで併記**している。

**ただし承認したのは「名称」の同一性だけである。** 区域の地理的境界が計画期を通じて不変である
ことは原資料のどこにも書かれておらず未検証で、実際に内訳の粒度は変化している
（r4 は3区分 → r6 は5区分）。yaml の `limitation` / `caveat_extent_changed` に明記した。

**(b) 水源系4語 — 否認した（証拠が弱いのではなく、原文が非同一を証明している）**

引き継ぎ資料は「階層関係の明文化」として保留していたが、原文を読むと**名寄せしてはならない**ことが分かる:

- 地域水源林エリア＝「…集水域のうち、**水源の森林エリアを除いた区域**」→ 両者は定義上**互いに排他**
- 「県内水源保全地域の生活排水処理率 95.5% / **うち**ダム集水域の生活排水処理率 74.1%」
  （`suigen_hozen_final_eval` p.54）→ ダム集水域 ⊂ 水源保全地域の**包含関係**

**`areas_mapping.yaml` に元から書かれていたフォーマット例
（`canonical: 水源保全地域 / aliases: [水源の森林エリア, 地域水源林エリア]`）は原文に照らして誤りである。**
そのまま採用すると、排他関係にある2エリアを同一視した誤ったデータセットになる。
階層・排他の関係は名寄せではない情報として `relations_do_not_merge` に分離して記録した。

**人間に残る確認事項**: (a) の**地理的境界**が計画期を通じて同一かどうか。
これは県自然環境保全課・現地専門家でないと確認できない。

**`moni1000_sites` を対象外とした根拠**: `scripts/collect_moni1000_sites.py` は公開HTMLの

判断の理由:
- **破棄しない**: 本件は「何が送信され何が取得されたか」の**監査証跡そのもの**である。
  消すと事後の追認・報告・是正のすべてが不可能になる。旧行を消さない方針（F-5）とも矛盾する。
- **保持（配布継続）もしない**: 配布元は「利用者ごとにアンケート回答＋規約同意」を条件に

  （**このデータはアプリDBにも DwC-A にも元々1行も入っていない**。`organism_records` は
  GBIF と iNaturalist のみ）。リスク対効果が完全に隔離側に傾く。
- COLLECTOR_CONTRACT の**当時から存在した**ライセンス規定「再配布不可・要申請のものは
  **ダウンロードせず** `register(redistributable=0, record_count=0, ...)` だけ残すこと」に照らすと、
  本来は取得しないのが正しい状態だった。隔離はそこへ近づける措置である。

**可逆性**: 追認が得られたら `redistributable=1` に戻すだけでよい。
**再取得（＝再度のフォーム送信）は不要。**

#### B-3. レッドデータブック2022 植物編 — 【判断済み】統合せず、版付き別テーブルで併存

**統合は不可能であることが実測で確定した。** 2022年版CSV（1,033行）は
**1,033行すべてで `scientific_name` が空欄**である。原資料（PDF p.10-39）に学名の記載が一切なく、
和名と科名しかないため（`cells.sqlite` notes.`n_rdb2022_plants_002` に原文あり）。
`taxa` は**学名を主キー**にしているので、学名キーでの統合は構造的にできない。

和名結合も機械的には成立しない。菌類では同一種が2020年版「和名なし〈オルフェラ・ハイシイ〉」／
2022年版「オルフェラ・ハイシイ*」のように表記が異なり、単純一致では取りこぼす。
さらに統合しても実利がない——`organism_records` へのRLカテゴリー付与は学名結合で行われるため、
学名のない2022年版を統合しても FR-4.5（希少種座標の一般化）には一切効かない。

**採った対応**: `taxa` を一切変更せず、`redlist_assessments` テーブル（2,884行）を新設して
版を併存させた（`scripts/c28_redlist_assessments.py`。冪等）。

#### B-4. 非商用・表示なしデータの扱い — 【判断済み】DwC-A から除外、マスタは全件保持

`noncommercial` と `unknown` は**法的性質が異なる**のに、従来は同一に扱われていた:

| license_class | 件数 | 法的性質 | DwC-A | マスタDB |
|---|---:|---|---|---|
| `open` (CC0/CC BY) | 625,386 | 追加条件なく再配布可 | 含む | 保持 |
| `restricted` (CC BY-SA/ND) | 679 | 商用可。SA/ND条件あり | 含む | 保持 |
| `noncommercial` (CC BY-NC系) | 176,397 | **出典明示＋非商用なら再配布可** | 除外 | 保持 |
| `unknown` (表示なし) | 21,230 | **許諾なし＝全著作権留保と見るべき** | 除外 | 保持 |

**採った対応**:

**マスタDB `data/db/ryuiki.sqlite` は 823,692件を全件保持する。** どの行が再配布・商用利用
できるかは `license_class` / `commercial_ok` 列で判別する（削除はしない）。
DwC-A は既定で `noncommercial` + `unknown` = 197,627件を除外し、626,065件を出力する。

第三者にデータを渡す場合の絞り込み:
```sql
-- 再配布・商用利用してよい行だけ
SELECT * FROM organism_records WHERE license_class IN ('open','restricted');
-- 同等（commercial_ok 列を使う場合）
SELECT * FROM organism_records WHERE commercial_ok = 1;
```

**当初は配布DB（`data/dist/ryuiki_public.sqlite`）から `unknown` を除外する処置も行ったが、
配布パッケージ自体を廃止したため対象が消滅した**（`docs/FINAL_REPORT.md` §0.3）。
`organism_records_dwca_safe` VIEW も配布DB専用の仕組みだったため消滅している。

**教訓（配布DBは無くなったが、絞り込みSQLを書くときは同じ罠がある）**:
当時の VIEW 定義は
`WHERE license_class IS NULL OR license_class NOT IN ('noncommercial','unknown')` となっており、
**NULL を「安全」側に通していた**。一方 `x01_dwca.py` は `r["license_class"] or "unknown"` で
NULL を除外側に倒しており、**2つの安全弁の向きが逆**だった。
**除外リスト方式（`NOT IN`）ではなく許可リスト方式（`IN ('open','restricted')`）で書くこと。**
そうすれば NULL や未知の値は自動的に「安全でない」側に落ちる。

**人間に残る確認事項**: データを第三者に渡す場合、NC 混在の是非と、OSM由来データの
ODbL Share-Alike 条件（`docs/LICENSE_MATRIX.md` §4.7）を法務的に確認すべき。

### E-2. 「流域界」は「県界クリップ」ではない
`nlni_w12_watersheds.geojson` の9水系の面積合計は 3,116km² で、**神奈川県面積 2,416km² を超える**。
相模川上流の桂川・道志川（山梨県域）、酒匂川上流（静岡県域）を含むため。

また **W12 に流域名は入っていない**（属性はコードのみ、公式の名称対応表が存在しない）。

### E-4. 意図的に埋めていない値（推測で埋めないこと）
| 項目 | 状態 | 理由 |
|---|---|---|
| `sites.treatment`（対策区/対照区） | 合成データで12地点のみ設定 | 公開データに存在しない |
| 相模原市大気の `unit` | NULL | 公開元に単位の記載がない |
| 気象庁の「--」（現象なし） | NULL（0ではない） | 0と区別する必要がある |
| 動物レッドリスト221件の `scientific_name` | 全件空欄 | **原資料に学名の記載が一切ない**（和名と日本語科名のみ） |
| A10 自然公園の公園名 | 空欄 | 原データに公園名フィールドが存在しない |
| DwC-A `occurrence.txt` の `scientificName` 216件 | 空欄 | 原資料に学名がない。推測で埋めていない |

**動物レッドリストに学名がないことの影響**: 82万件の出現記録に鳥類・哺乳類・魚類の
レッドリストカテゴリを**学名では結合できない**。和名結合か別途の学名対照が必要。
これは `FR-4.5`（希少種の位置を自動で粗く丸める）の実効性に直結する
——現在の一般化件数2,080件は、**学名が取れている分類群だけの数字**である。

### E-5. 環境省 公共用水域の測定点に欠測センチネル値
324点のうち **34点が `lat=-1, lon=-1`**（欠測を表す番兵値）。
`m01_sites.py` にフィルタを入れてあるが、生CSVを直接使う場合は自分で除外すること。

### E-6. DwC-A の `eventDate` を `YYYY-MM-DD` だけで検証しないこと
Darwin Core の `eventDate` は ISO 8601 の date / dateTime に加えて**「開始/終了」の区間表記**
（例 `2019-08-01/2019-08-31`）を許容する。GBIF由来には dateTime形式・区間形式が計17,162件含まれる。
`YYYY-MM-DD` のみを正とする検査を書くと、この17,162件を誤って「非適合」と判定する。
`scripts/x03_verify_dwca.py` は3形式すべてを適合として扱っており、その基準での非適合は0件。

## 5. 実装上の教訓（同じ罠を踏まないために）

### F-1. エラーの握り潰しが「無言の取得漏れ」を生む
GBIF 収集の初期実装は4並列で API を叩き、**HTTP 429 を例外処理で握り潰して空配列を返していた**。
結果、`expect=3486 got=0` が「正常終了」として記録され、**163,118件の取得漏れが発生**した。

検出できたのは**区画ごとに期待値と実取得数を突き合わせる設計だったから**。
この突合がなければ最後まで気づけなかった。

対策: 並列度1・`Retry-After` 準拠・指数バックオフ。最終的に 658,360件を回収。

### F-2. 「決定論的だから安全」は幻覚を防ぐだけで、正しさは保証しない
P1 Maker を pdfplumber の決定論的抽出にしたことで **C1（`source_text` の実在チェック）は全文書で
0件失敗**を達成した。幻覚は構造的に起きない。

しかし `clean_cell()` が**改行を区切り文字なしで除去**していたため、
`"1,316 12 481\n3,424..."` → `"1,316 12 4813,424..."` と隣接行の数値が融合し、
literal 一致が構造的に不可能になっていた。**幻覚ではないが、正しくもない。**

`scripts/p1_maker_v2.py` で座標クラスタリング方式に変えて改善:
- `biodic_6th`: 読取失敗 2,755 → 2,062 / 値ありセル 5,775 → 7,093
- `choju_higai_*`（5本）: 読取失敗 831 → **5** / 値ありセル 359 → **2,856**

**`p1_maker.py` は他文書で正常に動いているので改変していない。** v2 は対象文書にのみ適用。

### F-3. トリアージの診断を鵜呑みにしない
`docs/P5_triage.md` は `biodic_6th` の失敗を「**B. OCR品質＝テキスト抽出順序の破綻**」と分類していたが、
実測すると `extract_text()` の行順序は**正しかった**。真因は F-2 の通り別物だった。

**分類は仮説であって診断ではない。必ず実測で確かめること。**

### F-4. P2 Checker は決定論的コードにすべき
`docs/datacollection.md` は P1/P2/P3 をすべて LLM で回す前提だが、**C1〜C6 はすべて機械的に判定可能**。
決定論的コードにしたことで、速度・再現性・信頼性のすべてが向上した。
LLM が必要なのは P0（語彙抽出）・P4（注記抽出）・P3（画像からの読み取り）のみ。

### F-5. 旧行を消さずに supersede する
再抽出時は行の粒度が変わる（1マージ行 → 複数サブ行）ため 1対1 の UPDATE ができない。
`cells.superseded` 列を追加し、旧行は `superseded=1` にするだけで**削除していない**。
比較・監査・巻き戻しが可能。

この方針は `source_registry` にも適用した。GBIF の旧登録 `gbif_kanagawa` は
`REBUILD.md` が想定していた UPDATE では主キー衝突して統合できなかったため、
削除せず `notes` に `【SUPERSEDED】` を付けて無効化した（§1 参照）。

### F-6. 引き継ぎ資料の数字は、引き継いだ側が実測し直すこと
本タスクでは、前版の引き継ぎ資料に書かれていた「791件超過」「partition report が古い」
「source_id 孤児が残っている」の3点がいずれも実測と食い違っていた（§2-A 参照）。
いずれも**書かれた時点では正しかったが、その後の収集完走で状況が変わっていた**もの。
**引き継ぎ資料の数字は仮説として扱い、着手前に必ず実測で裏を取ること。**

### F-7. 検証は手作業ワンライナーではなくスクリプトに固定する
DwC-A の構造検証（meta.xml整合・eventID参照整合・列数不整合・ISO8601適合性）は
前タスクまで手作業で行われており、再現できなかった。本タスクで
`scripts/x03_verify_dwca.py` として固定した。**再実行して同じ結果が出せない検証は、検証ではない。**

## 7. 最初にやること（推奨順）

機械的作業（A）も判断（B）も完了している。残るのは**組織としての意思決定**と C の未着手項目。

1. **【最優先・人間にしかできない】B-2 の追認判断。**

   **追認するか撤回するか**を決める。追認するなら該当10ソースを `redistributable=1` に
   戻すだけでよい（データは全件残っているので再取得は不要）。
   なお送信された所属名は「NPO法人コード・フォー・ジャパン」で、**法人格が事実と異なる**。
   併せて `scripts/common.py` の UA に記載された個人アドレスの承諾状況を確認する。
   **次に収集スクリプトを走らせる前に必ず。**

   データを第三者に渡すなら、NC混在の是非と OSM の ODbL Share-Alike 条件（§4.7）の
   法務確認が要る

   **動物レッドリストの学名対照**（FR-4.5 の実効性に直結、E-4）

## 8. 連絡事項

- **`data/db/ryuiki.sqlite` と `cells.sqlite` は複数プロセスから書かれる想定**。
  接続時は必ず `sqlite3.connect(..., timeout=60)` + `PRAGMA busy_timeout=60000`
- 全収集スクリプトは `data/raw/` のキャッシュを見るため、**再実行しても再ダウンロードは発生しない**
- 外部サービスへのアカウント登録・API key 取得は**このプロジェクトでは禁止**としてきた。
  方針を変える場合は `docs/COLLECTOR_CONTRACT.md` も更新すること
- リポジトリはまだ1コミットもされていない（全ファイルが untracked）。
  コミットする場合、`data/db`(720MB)・`data/dwca`(413MB)・`data/processed`(4.4GB)
  が現状 `.gitignore` の対象外である点に注意（`data/raw` と `data/logs` のみ除外されている）。
