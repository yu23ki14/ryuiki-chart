## 0. 結論（1行）

**新規リポジトリを作らず、この `ryuiki-demo` に `/water` として相乗りする。**
DuckDB / Python / tippecanoe はそれぞれ「既にあるもの」で置き換える。

設計図が「県内の任意の地点 → 水源 → その川」という導線を求めているのに対し、
このリポジトリは既に「その川」の側（流域界・河川流路・水質・生物相）を持っている。
別リポジトリにすると導線が切れるので、相乗りが唯一の選択肢になる。

## 4. タイル形式の判断（PMTiles を今は入れない）

設計図は tippecanoe → PMTiles を前提にしているが、このリポジトリの既存経路は
「GeoJSON を静的アセットに置き、ブラウザが直接取る」（`/geo/rivers.geojson` が 4.5MB でこれをやっている）。

- 神奈川県の町丁目はおよそ 1 万ポリゴン。生の GeoJSON は 100MB 級だが、
  表示に要る精度（tolerance ≒ 5m）まで簡略化すると経験的に 15〜30MB。
- **MVP（横浜市のみ）は約 3,300 ポリゴン**。簡略化すれば数MBで、既存経路にそのまま乗る。
- Cloudflare の静的アセットは 1 ファイル 25MiB 上限。県全域で GeoJSON はここに触れうる。

**方針**: Phase 1（横浜のみ）は GeoJSON。Phase 3 で県全域に広げるときに実測し、
簡略化後（gzip 前）が 8MB を超えたら PMTiles に切り替える。切り替えのコストは
`tippecanoe`（`ghcr.io/felt/tippecanoe` の docker イメージで回す。ホストに入れない）と
`pmtiles` npm パッケージ 1 つ、`MapCanvas` に protocol 登録 1 行。前倒しする理由が無い。

**dissolve はしない**。隣接町丁目を水源比率で融合すればポリゴン数は激減するが、
CP0 の完了条件「タップすると key_code と町丁目名が出る」が満たせなくなる。

## 5. D1 を読まずに済ませる

水源カードに出す内容（水源名・比率・確信度・根拠資料）はすべてビルド時に確定するので、
タイル/GeoJSON の属性に焼き込めばフロントは D1 を触らない。設計図の「サーバーコストゼロ」はここで守る。

D1 に入れるのは次の 2 つの用途のみ。

1. **監査**: `flow_edge` / `zone_assignment` / `source_doc` を D1 にも入れ、
   AI アシスタントと（開けたときの）データ探索から引けるようにする。
2. **既存画面との接続**: `source_doc` は既存の `source_registry` にも `common.register()` で登録し、
   `/sources` に出す。水源河川は既存の `river_segments` / `nlni_w05_rivers` の `name_ja` に名寄せし、
   水源カードから `/map` の該当流域へ飛ばす（＝「その川はどうなっているか」の導線）。

導線 2 は設計図に無いが、依頼の出発点（「生活とつなげたい」）そのものなので Phase 1 の範囲に入れる。

## 6. Git 管理の扱い（2026-09-05 決定）

ルート `.gitignore` は `data/*` を丸ごと除外している（14GB あり、すべてスクリプトで再生成できるため。
例外は再取得不能な `data/vocab/` のみ）。

- `data/water/*.csv` は **人と Agent が PDF を読んで手で作るもので、再生成できない**。
  `data/vocab/` と同じ理由で `!data/water/` の例外を足して **Git 管理下に置く**。これは確定でよい。
- `docs/sources/` への PDF 保存（設計図 §6-4「リンク切れ対策」）は保留。
  - Git に入れる → 事業体 PDF は数十MB〜になり、再配布可否も `docs/LICENSE_MATRIX.md` の
    区分で個別確認が要る。
  - 入れない（`data/raw/water/` に置いて gitignore）→ クローンし直すと消える。
    `source_doc` に URL・`retrieved_at`・sha256 を持たせて再取得できるようにはできるが、
    ページごと消えた場合は復元できない。
  - **決定（2026-09-05・司令塔）**: **PDF は Git 管理外。** `data/raw/water/` に置き、
    `source_doc.csv` に URL + sha256 + `retrieved_at` を必ず記録する（`c91_water_docs.py` が書く）。
    リンク切れが実際に起きた資料だけ、再配布可を確認のうえ個別に Git へ入れる。

### 実測（作業2の結果。§4 の判断の根拠）

- 2020年国勢調査 小地域（Shapefile, 世界測地系緯度経度）は appId 無しで取得できる。
  `A002005212020DDSWC14.zip` 5.0MB。
- 原本 5,372 レコード。水面調査区（HCODE=8154）10 件を除外し、
  分断された町丁目 273 レコードを KEY_CODE で MultiPolygon に統合して **5,089 町丁目**。
  横浜市は 1,741。
- 人口の合計が 9,237,337 で、2020年国勢調査の神奈川県人口と一致（読み違いが無いことの確認）。
- 簡略化後のサイズ:

  | tolerance | ≒距離 | GeoJSON |
  |---|---|---|
  | なし | – | 21.7 MB |
  | 0.00002 | 2.2 m | 11.4 MB |
  | **0.00005** | **5.5 m** | **8.0 MB** ← 採用 |
  | 0.0001 | 11.1 m | 5.9 MB |
  | 0.0005 | 55.5 m | 2.7 MB |

  採用値で属性を焼き込んだ `water_zones.geojson` が **8.1MB**。
  既存の `rivers.geojson`（4.5MB）と同じ配り方で載る。Cloudflare の 25MiB 上限にも余裕があり、
  **PMTiles は要らない**（§4 の判断はこれで確定）。`build-water-geo.mjs` は 20MB を超えたら警告を出す。

### 検証したこと

- `water_lib.validate()` — 主キー重複・語彙外・FK 切れ・自己参照の閉路・
  `share` 合計 ≠ 1.0・期間の逆転・`source_doc_id` 無しの行を、
  わざと壊した CSV で全部検出することを確認。エラーがあれば DB に何も書かない。
- `water_lib.compose()` — 2 段ブレンド（企業団→横浜のような卸→末端）を含む再帰合成が
  手計算と一致することを確認。経路のいちばん弱い `confidence` / `basis` が残る。
  上流が未入力の施設は 0 で埋めず「未解決」として別に返す。
- MapLibre のスタイル式を `@maplibre/maplibre-gl-style-spec` で検証。
  **割付が 1 件も無いとき `match` 式は組が 0 個になり不正**（`addLayer` が投げて地図が真っ白）。
  Phase 0 はまさにその状態なので、水源が 0 件のときは定数色にする分岐を入れてある。

### 分かっている未解決

- **ホストのローカル D1 が空**。`web/.wrangler/state/.../` に 1.2GB のシード済み SQLite があるが、
  それは `wrangler.jsonc` の `database_id` がプレースホルダだった頃のファイルで、本番 ID に
  差し替えた今は miniflare が別名の空ファイルを見ている。`/`・`/sites`・`/sources` が
  ローカルで 500 になるのはこのため（`/water` は D1 を読まないので影響しない）。
  この件は水源マップとは無関係で、直すなら `pnpm run db:setup` を流し直す。
  ただし `seed-d1-local.mjs` は D1 の SQLite が 2 つあると「一意に決められない」で止まるので、
  古い方を消すかどうかの判断が要る（1.2GB あり、消すと再シードに時間がかかる）。
- 画像 PDF の OCR エンジンが手元に無い。Phase 1 で事業体の資料が画像だった場合に要る
  （設計図 §7 のリスク欄）。`pdftoppm` はあるので画像化まではできる。

### 「比率は出さないが顔ぶれは出す」— basis=unknown（2026-09-05・司令塔決定）

県営水道の相模原・平塚・厚木などは、資料が「この市には寒川浄水場西系と企業団伊勢原の水が入る」と
**顔ぶれまでは言っているのに、混合比だけが非公表**という状態だった。当初これを全部「不明」にしていて
人口カバレッジが 51.2% に留まった。3 案を比べた結果、**比率だけ黙る**を採った。

| 案 | カバレッジ | 性質 |
|---|---|---|
| A そのまま「不明」 | 51.2% | 資料が言っていることまで捨てている |
| B 事業体全体の平均を当てる（相模川 74.2% / 酒匂川 24.5%） | 73.4% | 正確だが**場所固有でない**。藤沢に過小・伊勢原に過大 |
| **C 顔ぶれだけ出して比率を出さない** | **68.5%** | **場所固有で、かつ捏造しない** |

実装（`scripts/water_lib.py`）:

- `flow_edge.basis` に **`unknown`** を追加。意味は「上流の顔ぶれは資料で確定しているが混合比が非公表」
- `basis=unknown` の行は **`share` を空にする**。0.5 や施設能力比で埋めると検証がエラーにする
- **同じ流入先に、比率のある行と `unknown` の行を混ぜるのは禁止**。混ぜると片方だけ % が出て、
  残りが 0% なのか不明なのか読めなくなる
- 合成は、経路に `unknown` が 1 本でもあればその町丁目の水源を**全部まとめて比率なし**にする
- 施設能力比で概算が置ける場合は `unknown` ではなく従来どおり `nominal`。**両者は別物**

画面（`WaterPage.tsx` / `lib/map/stripe.ts`）:

- 比率不明の町丁目は、関係する 2 水源の色の**斜めストライプ**（MapLibre の `fill-pattern`）で塗る。
  単色だと「主にこちら」に見え、グレーだと「何も分かっていない」に見えるため、どちらでもない見せ方にした
- パターンは出現した組み合わせから動的生成。実データでは相模川＋酒匂川の 1 種類
- カードは % の帯も数字も出さず（`0%` も `--%` も出さない）、水源名と
  「混合比は公表されていません」だけを出す
- 塗りは 2 レイヤに分けてある（`ry-water-fill` は `["!",["has","mixed"]]`、`ry-water-mixed` は `["has","mixed"]`）。
  組み合わせが 0 件のときは mixed レイヤを足さない（画像が無いまま `fill-pattern` のレイヤを足すと面が描かれない）

### 地図の色数（2026-09-05 に対処）

Phase 2 の終わりに最上位水源が 5 色になり、`palette.ts` の `MAX_SERIES_ALLPAIRS=3`
（地図のように全ペアが同時に見える形では先頭 3 色まで）を超えていた。Phase 3 の頭で直した。

**元の作りの問題は色数だけではなかった。** 色を「割り付いた町丁目数の多い順」に
`SERIES[i % SERIES.length]` で配っていたので、

- 事業体を足すたびに**色が入れ替わる**（`palette.ts` の「順位で塗り替えない」に反する）
- 9 種類目からは**循環**して同じ色が 2 つの水源に付く（同「循環させない」に反する）

**直した形**: 水源 id に色を固定する。

| 水源 | 色 |
|---|---|
| 相模川 `SRC_SAGAMI` | `SERIES[0]` |
| 酒匂川 `SRC_SAKAWA` | `SERIES[1]` |
| 道志川 `SRC_DOSHI` | `SERIES[2]` |
| **それ以外（地下水・湧水・小河川）** | **`SERIES[4]`「その他の水源」に束ねる** |
| 未割付 | 灰（`#d5dbd9`） |

神奈川県の水道水はほぼ 3 河川に集約されるので、そこへ 3 色を固定で当て、残りは 1 つに束ねた。
4 色目は青・橙・緑と色相がいちばん離れる `SERIES[4]` を選んだ。
**3 色を超えるのは規約からの逸脱**だが、束ねなければ Phase 3 の地下水系で 10 色を超える。
束ねるのは**地図の塗りだけ**で、水源カードは実際の水源名（「秦野市の地下水」など）を出す。
凡例の「その他の水源」行には中身の名前を並べる。

塗りの式は `["match", ["coalesce",["get","s1"],""], "", 灰, SRC_SAGAMI, …, その他の色]` の形。
**空文字（＝未割付）を先に拾うこと。** `ry-water-fill` レイヤの filter は `mixed` を外すだけで
未割付は通ってくるので、既定値に落とすと未割付が「その他の水源」の色で塗られる。
`@maplibre/maplibre-gl-style-spec` で 6 ケース（未割付・3 河川・その他 2 種）を評価して確かめてある。

ストライプ（比率非公表）は実際の水源 id で色を引くので、束ね方を変えると縞の色も変わる。
`WaterPage.tsx` の `MAJOR_COLOR` と `lib/map/stripe.ts` は一緒に見ること。**その場しのぎで色を足さない。**
