# `variable_alias.csv` の stat/grain 一次資料調査

対象: `registry/variable_alias.csv` の `(dataset, alias, source_id)` 単位への分割
（申し送り #1）にあたって、`env_kousui_annual_kanagawa` / `env_kousui_sample_kanagawa` /
`atsugi_river_water_quality` / `jma_daily_yokohama` / `jma_monthly_kanagawa` の各組と、
`common:variable:hydro.flow`（`流量関連（公式定義未確認のため原表記のまま）`）の公式定義を
一次資料で確認した記録。**`variable_alias.csv` の `note` 列にはこの文書へのファイル参照
（`docs/plans/PHASE_B_ALIAS_STAT_SOURCES.md §…`）だけを書き、URL と引用の全文はここに置く。**

**原則**: 確認できたことだけを「確定」とし、引用元 URL と原文引用を必ず添える。
値の一致を確認した場合も「一致を確認した」という事実として書き、そこから統計量を逆算して断定しない
（例外的に JMA は原文書ではなく「気象庁が実際に公開している表の列見出し構造」自体を一次資料として読み、
さらに手元データで数値照合まで行った — これは値からの推測ではなく、公開された表の構造そのものの確認）。

## 1. 要約

調査対象とした (alias, source_id) は合計 **98 組**（年間値 45 / 検体値 16 / 厚木市 5 / JMA 日別値・月別値
16 datastream × 2 source_id = 32）。うち

- **確定 96 組**（stat・grain を一次資料または一次資料からの直接引用で確定）
- **未確認 2 組**（`大腸菌数`（素の値, `env_kousui_annual_kanagawa`）／`底層溶存酸素量`（`env_kousui_annual_kanagawa`））

確定した中にも、根拠の強さに差がある注記付きのものが数件ある（4節「確定の中の留保」参照）。

### 設計に影響する主な発見

1. **`atsugi_river_water_quality` の「mixed」は統計量の混在ではなく日付精度の混在だった。**
   全19本の原本xlsxに共通して「※数値は日間平均値です。」の注記があり、
   平成14〜令和2年度まで一貫して **stat=日間平均値（mean）**。年度2005以降 `measured_on` が
   年だけになるのは `scripts/m05_tier1.py` の `measured_on = sampled_on or fiscal_year` という
   フォールバックの結果で、**月は `source_ref`（`...xlsx#令和2年4月:相模川:pH` の形）に
   全行分残っている**ことを確認した（全19年度×12ヶ月、欠落なし）。つまり grain は
   「日 or 年」の混在ではなく「日 or 月」に直せる。ただし「日」のうち平成17年度(2005)以降は
   採水日が「8～9日」のような2日レンジ表記で、どちらの日にどの河川を採水したかは原本に
   記載がなく単一日付には確定できない（収集スクリプトの既存の扱いは正しい）。
   → **`grain='mixed'` は統計量の混在ではないので、`variable_alias` に `grain_rule` のような
   「行ごとに決まる」宣言的な列は不要と判断した。5組とも `grain='day'`・`stat='mean'` で確定する。**
2. **JMA月別値の「気温_最高」は日別値の「気温_最高」の平均ではなく、月内の極値（最大値）だった。**
   月別値の生表（`monthly_s1.php`）は列見出しが `気温(℃) → 平均 → {日平均,日最高,日最低}` と
   `気温(℃) → 最高 → 最高` / `→ 最低 → 最低` の**2系統に分かれており**、
   `variable_alias.csv` の `気温_最高`/`気温_最低` datastream 名は後者（極値）に対応する列である。
   2024年横浜の日別値12ヶ月分と月別値を突き合わせ、月別値の `気温_最高` が
   その月の日別値 `気温_最高` の **最大値と完全一致**することを数値で確認した。
   同様に `降水量_合計`は月合計、`降水量_最大_1時間`/`最大_10分間`は月内の日別値の最大と完全一致、
   `日照 時間`は月合計、`湿度_平均`/`気圧_現地_平均`/`風向・風速_平均 風速`は日別値の平均の平均、
   `湿度_最小`/`風向・風速_最大瞬間風速_風速`は月内の日別値の極値と完全一致することを確認した。
3. **`flowrate`（`流量関連（公式定義未確認のため原表記のまま）`）の公式定義が判明した。**
   環境省 公共用水域水質**検体値**データファイル利用説明書（国立環境研究所, 平成27年4月）の
   一般項目ファイルレイアウトに「流量」項目ID `090700`、単位 `m3/s` と明記されていた。
   該当する `measurements` 全4,668行はすべて `env_kousui_sample_kanagawa` から来ており
   （`kosui_k08` = 検体値・一般項目、まさにこの表に対応）、他 source_id には出現しない。
   **`variable.yaml` の `name_ja`/`unit_id`/`status` への反映は `phase-b/variable-flow` で
   完了済み**（詳細な反証可能性の検討は §3.3）。
4. **健康項目（cd, cn, pb, cr6, ass, thg, srhg, pcb 等27項目）は全て `env_kousui_annual_kanagawa` 由来**で、
   `env_kousui_sample_kanagawa` には出現しない。従来の `variable_alias.csv` の note は
   「環境省 公共用水域水質データファイル利用説明書（**検体値**）第1版(2012-08-22)」を引用していたが、
   実際に該当するのは**年間値**データファイル利用説明書（`MD_manu.pdf`）であり、
   従来の note の出典表記は誤りだった（本PRで修正する）。
5. **健康項目の「素の値」は全シアンを除き年間平均値、全シアンだけ最大値で評価される**ことが
   環境省の環境基準運用文書で確認できた。ただし新しい `zip_create` API のCSVは項目ごとに
   数値列が1本しかなく（旧NIES manual の「最大値」「平均値」2本立てとは異なる）、
   この1本の列が実際にどちらを格納しているかを直接記載した資料は見つからなかった
   （3.1節・4節を参照。特に `cn` は要注意）。

### 2.1 年度 vs 暦年（grain=fiscal_year の根拠）

MD_manu.pdf「１．ファイル仕様」より引用:

> 収録年度　昭和46（1971）～平成21（2009）年度

「収録**年度**」という語自体（「収録年」ではない）が、日本の行政データで標準的な
年度（4月〜翌3月）を意味する。検体値マニュアルにも同じ書式:

> 収録年度　昭和56(1981)～平成21（2009年度）

両ファイルとも measured_on の起点は「測定年度」（4桁整数・西暦年）であり、
検体値では別途「採取年月日時分」で実際の暦日が記録される（後述2.2）。
→ **grain='fiscal_year' は確定**（年間値ファイル全体に共通）。

### 2.2 生活環境項目・全窒素全燐（BOD, COD, DO, SS, 大腸菌群数, ヘキサン, TN, TP）

BODを例に原文引用（項目27〜38）:

> x_BOD／y_BOD／**C_BOD_日間平均値_平均値／BOD_日間平均値_平均値**／
> C_BOD_日間平均値_中央値／BOD_日間平均値_中央値／**C_BOD_日間平均値_75%値／BOD_日間平均値_75%値**

### 2.4 健康項目（cd, cn, pb, cr6, ass, thg, srhg, pcb, f, b, n14jiokisan 等27項目）

### 3.3 flowrate（流量）の公式定義

MK_manu.pdf「２．データレイアウト(1)一般項目ファイル」より原文引用（項目19、90700）:

`data/raw/env_kousui/kosui_k08_14_2015.zip` の実列 `FLOWRATE` を確認し、`measurements` の
`流量関連（公式定義未確認のため原表記のまま）`（variable_en=`river_width_or_flow`）全4,668行が
すべて `env_kousui_sample_kanagawa` から来ている（`k08`=一般項目、他 source_id には出現しない）
ことをDBで確認した。

| alias | source_id | 意味 | 単位 | grain | 根拠 |
|---|---|---|---|---|---|
| 流量関連（公式定義未確認のため原表記のまま） | env_kousui_sample_kanagawa | 流量（河川の流量） | m3/s | day | MK_manu.pdf「一般項目ファイル」項目19（090700） |

#### 反証可能性の検討: `FLOW` 列・川幅の可能性を排除する

同定に対する自然な疑義は「`FLOW` という別列があるのに、なぜ `FLOWRATE`＝090700 と言えるのか。
`FLOWRATE` が実は川幅を表している可能性は排除できているのか」である。`kosui_k08` の実列は
以下の並びを持つ（`RECORDID` 等のメタ列を省いた実測値部分）:

> ... WEATHER, FLOW, ODOR, HUE, TEMPERATURE, TEMPERATURE2, WTEMP, WTEMP2,
> FLOWRATE, FLOWRATE2, DEPTH, DEPTH2, CLEARNESS, CLEARNESS2

以下4点の根拠で、この疑義は排除できる。

1. **`FLOW` は数値項目ではない。** `FLOW` は `'00'` のような2桁のコード値（流況区分の
   カテゴリ値）であり、`scripts/c12_env_kousui.py` の `META_COLS`
   （`{"weather", "flow", "odor", "hue", "all2", ...}`）で既にメタ情報として除外済み。
   同スクリプトの `find_measure_cols()` は「値列 X は X2 または X3 という兄弟列を持つ」
   ことを機械的な検出条件にしており、`FLOW` にはその兄弟列（`FLOW2`）が無いため、
   そもそも測定値としては抽出されていない。`FLOWRATE` との同定を疑うにあたって、
   `FLOW` は数値項目ですらないので候補になりえない。
2. **`FLOWRATE` は数値項目で、小数を持つ兄弟列 `FLOWRATE2` を持つ。** `melt()` の
   `style='k'`（検体値ファイル）の規約は「`X`=値・`X2`=小数値・`X3`=フラグ」の3列構造
   （関数のdocstring参照）。`FLOWRATE`/`FLOWRATE2` の組はこの構造どおりで、単独のコード
   列である `FLOW` とは形自体が異なる。この出典で数値の測定項目は必ずこの3列構造に
   乗っており、`FLOWRATE` はその条件を満たす。
3. **列の並びが項目IDの並びと対応する。** MK_manu.pdf の一般項目ファイルレイアウトは、
   `090700`「流量」（項目19、原文引用は上記）の直前に `090500`「気温」・`090600`「水温」が
   並ぶ連番になっている（§3.4 の「気温」「水温」の行も同じレイアウトの隣接項目として
   個別に確定済み）。実列の並びも `..., TEMPERATURE, TEMPERATURE2, WTEMP, WTEMP2,
   FLOWRATE, FLOWRATE2, ...` と同じ順序になっており、気温・水温の列位置が確定している
   以上、その直後の値列（`FLOWRATE`）が `090700`「流量」であることは、項目IDと実列の
   両方が同じ連番構造を持つことから導かれる（偶然の一致ではない）。
4. **負の値の分布が「川幅」ではなく「流量」であることを支持する。** `FLOWRATE` には
   負の値が180行ある（全4,668行の3.9%）。この180行は83地点中14地点に集中しており
   （瀬戸橋/宮川30行、平潟橋/侍従川24行、夫婦橋/平作川22行、追浜橋/鷹取川21行、
   竹川合流後18行、入江橋/入江川16行、清水橋/大岡川12行、渚橋/田越川10行、他6地点
   合計27行）、いずれも感潮域（河口付近で潮汐の影響を受ける区間）の地点である。
   全体の値の範囲は最小-8.5〜最大81。**川幅が負の値になることは物理的にありえないが、
   潮汐による逆流は流量(m3/s)として物理的に整合する。** つまり負の値は同定への反証では
   なく、むしろ「これは川幅ではなく流量である」ことを支持する証拠になる
   （`data/db/ryuiki.sqlite` を読み取り専用で開き、
   `variable_en='river_width_or_flow' AND source_id='env_kousui_sample_kanagawa'` で
   集計。件数・min/max・地点数を実測確認済み）。

**この発見は `phase-b/variable-flow` で `registry/variable.yaml`
（`common:variable:hydro.flow` の `name_ja`/`unit_id`/`status`）に反映済み**
（`name_ja`="流量"、`unit_id`=`common:unit:m3_per_s`、`status`="ok"）。反映の経緯は
`docs/plans/PHASE_B_INTAKE.md` の該当節を参照。

### 4.3 「年だけ」の実態は「月は分かるが日が特定できない」だった

`m05_tier1.py` の `load_measurements_csv()` は
`measured_on = text(sampled_on) or text(fiscal_year)` というフォールバックで、
`sampled_on` が null（2005年度以降）の行はDB上 `measured_on` が年度の数字（例:`"2020"`）だけになる。
これが「2005年度以降は測定日が年だけ768行」の実体。

しかし `source_ref` 列（`{resource_url}#{month_label}:{site_raw}:{variable_ja}` 形式、
例: `.../kougai_kasen_r02data.xlsx#令和2年4月:相模川:pH`）には**月ラベルが必ず含まれている**。
`data/processed/atsugi_river_water_quality.jsonl` 全4,560行の `source_ref` を年度別に集計し、
**全19年度×12ヶ月がすべて欠落なく存在する**ことを確認した。

→ **`atsugi_river_water_quality` の grain='mixed' は「日 or 年」の混在ではなく、実態は
「日（2002-2004年度）or 月まで確定できるが日は範囲でしか分からない（2005年度以降）」である。**
`source_ref` をパースすれば2005年度以降も grain='month' まで引き上げられる
（`measured_on` の生成ロジックを変えれば良く、原本データを再収集する必要はない。Phase B の課題として
`docs/plans/PHASE_B_INTAKE.md` に残す）。**本PRでは `measured_on` の生成ロジックには触れず、
grain='day' のまま登録する**（stat/grain の分割だけが本PRのスコープ）。

## 5. 気象庁 日別値・月別値（`jma_daily_yokohama` / `jma_monthly_kanagawa`）

### 5.1 手法

気象庁の用語解説ページ（`data.jma.go.jp/stats/etrn/help2.html` 等）を探索したが404、または

**気象庁が発行する表そのものの列見出し（多段ヘッダ）構造**を確認する形。

### 5.2 列見出し構造の確認

月別値（`monthly_47670_2020.html` 等）の気温列見出し（`pandas.read_html` で取得した多段タプル）:

```
('気温(℃)', '平均', '日平均')
('気温(℃)', '平均', '日最高')
('気温(℃)', '平均', '日最低')
('気温(℃)', '最高', '最高')
('気温(℃)', '最低', '最低')
```

日別値（`daily_47670_202504.html`）の気温列見出し:

```
('気温(℃)', '気温(℃)', '最高', '最高')
('気温(℃)', '気温(℃)', '最低', '最低')
```

**確定はしたが留保が付くもの**（未確認とは別枠、4節参照）:

- 健康項目のうち `cn`（全シアン）: 環境基準の評価方法としては「最高値」と確定しているが、
  `zip_create` API の実CSV列 `cn`（1項目1数値列）が実際に最大値を格納しているのか、
  他の健康項目と同じ平均値のままなのかは、列レイアウトを明記した資料が見つからず未確認。
- `全亜鉛`/`ノニルフェノール`/`LAS`: 環境基準の基準値が年間平均値であることは確定したが、
  それが `zip_create` API のCSV列の集計方法と同一である保証（列レイアウト表）は見つかっていない。
- `env_kousui_sample_kanagawa` の全16 alias: 検体値ファイルの一般原則（レコード=1回の測定）は
  確定したが、調査区分コード5/6（水質自動モニター＝日間平均値）に該当する行が混在している

- `atsugi_river_water_quality` の2005年度以降: stat=mean（日間平均値）は確定したが、
  4河川のうちどれがレンジ内のどちらの日に採水されたかは原本に記載がなく、
  単一の採水日には永久に確定できない（データの限界であり、追加調査で解決する見込みはない）。

## 7. 数値照合の手順まとめ（再掲）

1. `data/raw/jma/daily_47670_202401.html` 〜 `202412.html`（気象庁公式サイトの生HTML表、
   `scripts/c10_jma.py` が取得しローカル保存済み）を `pandas.read_html` で読み込み、
   多段見出しをフラット化。
2. 「日」列が数字である行（月内の実測日、末尾の集計行を除外）だけを抽出。
3. 変数ごとに月内の 最大値／最小値／合計／平均 を計算。
4. `data/raw/jma/monthly_47670_2024.html` の対応する月・対応する変数の値と突き合わせ、
   一致するかを1ヶ月ずつ12ヶ月分確認（結果は5.3節の表の通り、全項目で一致）。
5. 一致した事実のみを記録し、「一致したから stat はこれだ」という逆方向の断定はせず、
   気象庁自身の表の列見出し構造（5.2節）と合わせて確認した。
