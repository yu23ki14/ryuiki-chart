## 0.3 再々々追記: 配布パッケージ（`data/dist/`）の廃止

**プロジェクトオーナーの判断により、配布パッケージを廃止した（2026-08-29）。**

`data/dist/` は「第三者に渡してよい分だけを選り分けてコピーした一式」だったが、
5.0GB のうち 4.4GB は `data/processed/` の単純コピーであり、**元データの重複でしかなかった**。
データセットを第三者に渡す予定がない以上、二重管理が混乱を招くだけと判断された。

### 削除したもの

| 対象 | サイズ | 備考 |
|---|---:|---|
| `data/dist/` ディレクトリ一式 | 5.0GB | `ryuiki_public.sqlite` / `processed/` / `README.md` / `EXCLUDED.md` / `_build_plan.json` |
| `scripts/x02_build_dist.py` | — | 配布パッケージ構築スクリプト |
| `data/dwca_ryuiki_kanagawa.zip` | 3KB | 14:47時点の古いビルド残骸（`data/` 直下にあった紛らわしいファイル） |

### 保全したもの

- **DwC-A の zip は `data/dwca/dwca_ryuiki_kanagawa.zip` に移した**（29.2MB）。
  展開形（`event.txt` 等）と同じディレクトリに置いてある。
  `scripts/x01_dwca.py` の出力先も `data/dwca/` に変更済みなので、再生成しても同じ場所に出る。
- マスタDB `data/db/ryuiki.sqlite`（823,692件）、`data/processed/`、`data/raw/` はいずれも無改変。

### ライセンス判断の位置づけがどう変わったか

配布パッケージが無くなっても**ライセンス台帳（`docs/LICENSE_MATRIX.md`）の判断は有効**である。
変わったのは「判断を機械的に適用する先」だけ:

| | 廃止前 | 廃止後 |
|---|---|---|
| ソース単位（`redistributable`） | DwC-A と配布パッケージの両方に適用 | **DwC-A のみ**に適用 |
| レコード単位（`license_class`） | DwC-A から noncommercial/unknown を除外＋配布DBから unknown を除外 | **DwC-A から noncommercial/unknown を除外**（従来どおり） |
| マスタDB | 全件保持 | 全件保持（変更なし） |

したがって **B-4 で行った「配布DBから `unknown` を除外する」処置は、対象そのものが無くなった**。
マスタDBは従来どおり 823,692件を全件保持し、どの行が再配布・商用利用できるかは
`license_class` / `commercial_ok` 列で判別する。DwC-A（626,065件）は変更していない。

`organism_records_dwca_safe` VIEW も配布DB専用の仕組みだったため消滅した。同等の絞り込みは
`WHERE license_class IN ('open','restricted')` または `WHERE commercial_ok = 1` で行う。

### B-2（moni1000）の隔離はどうなったか

`redistributable=0` という**台帳上の記録として有効なまま**である。
配布パッケージが無くなったので「配布物から除外される」という効果は消えたが、
「このデータは第三者に再配布できない」という判断そのものは `source_registry` に残っている。
データは `data/raw/`（生zip 8本・167MB）と `data/processed/`（CSV/JSONL 10ファイル）に全件保全。

判定基準: 「本データセット（`data/db/ryuiki.sqlite` / `data/processed/` / `data/dwca/`）だけで、要求定義書の当該要求が
どの程度デモ可能か」。アプリのUI・API・認証・通知等の実装そのものはこのタスクのスコープ外（データ
基盤のみ）であるため、「実演可能」は原則として「対応するデータが実在し、かつ意味のある値が入っている」
ことを指す。**要求定義書が要求する情報のうち公開データに存在しないもの（観測者・機器校正・現地測定
イベント・品質遷移履歴・介入記録・意思決定記録等）の多くは、`scripts/s01_synthetic.py` が生成した
合成データ（`is_synthetic=1`）によって実演可能になっている（`docs/SYNTHETIC_DATA.md` 参照）。合成データは
実データの分布から乱数生成した“それらしい値”であり、実際の測定結果ではない点に注意。**

## 3. 既知の限界

### 3.1 本タスク（パッケージング）で発見・対応した問題

1. **FR-4.5 希少種位置一般化のバグ**: `scripts/x01_dwca.py` の旧実装は `red_list_category` の原表記全体（例:「絶滅危惧Ⅱ類（VU）」、全角ローマ数字を含む）が `SENSITIVE` 集合の要素と完全一致するかだけを見ており、実データでは一件も一致せず `n_gen` は常に0だった。本タスクで、末尾の括弧内コード（CR/EN/VU/EX/EW/CR+EN）だけを 抽出して判定するよう修正し、実データで機能することを確認した（本書§4参照）。
2. **GBIF収集の未完了とsource_registry未登録 → 解消済み（§0.1）**: `scripts/c02_gbif.py` の完走ログで 多数の区画が HTTP 429 により `got=0` となっており、修復スクリプト `scripts/c02_gbif_repair.py` が実行されたが、これも持続的な429エラーにより 160件中38件処理した時点でプロセスが終了し、最終的な register(...) 呼び出しに到達しなかった。その後の第2・第3ラウンドで回収が進み、**2026-08-29の第3ラウンドで完走**（`data/logs/gbif_repair_run3.log`）、`source_registry` に `gbif_kanagawa_occurrences`（658,360行・`redistributable=1`）として登録された。本再追記タスクで `docs/REBUILD.md` の手順を実行し、GBIF由来行はDwC-A出力に反映済みである（§0.1・§5）。なお最終突合では GBIF側 count=659,399 に対し **1,039件が未取得のまま残っている**（区画取得不能93件＋日付フィールド欠損により分割取得できない958件）。区画別の内訳は `data/logs/gbif_partition_report.csv` に記録済みで、**データ側を操作して件数を合わせることはしていない**。
3. **GBIFのsource_id命名不整合 → 本タスクで修正**: `c02_gbif.py`/`c02_gbif_repair.py` が`register()`する際のsource_idは以前`"gbif_kanagawa"`だったが、`m03_organisms.py`が`organism_records.source_id`に実際に格納する値は`"gbif_kanagawa_occurrences"`であり、文字列として一致しなかった。本タスク（§0）で、他スクリプトが`"gbif_kanagawa"`という文字列を参照していないことを`grep -rn`で確認したうえで、`c02_gbif.py`・`c02_gbif_repair.py`の`register()`呼び出しを実データ側の名称`"gbif_kanagawa_occurrences"`に統一修正した。ただし本タスク実行開始時点で既に起動していたGBIF収集プロセスは修正前のコードで動作中のため、その回の完走時になお旧名で登録される可能性が残る。`x01_dwca.py`はいずれの名前でも動作するようエイリアス解決（`{'gbif_kanagawa_occurrences': 'gbif_kanagawa'}`）を引き続き維持している。全ソース・全テーブルを対象にした孤児検査を実施し、`data/processed/source_id_orphans.csv`に出力した。検査の結果、`sensor_timeseries.source_id='synthetic_sensor'`（19,420件）という別の孤児も発見し、`source_registry`に登録して解消した。残る孤児は`gbif_kanagawa_occurrences`のみで、上記の理由により本タスク内では完全解消できない（`docs/REBUILD.md`参照）。
   - **【再追記タスクで解消】** 第3ラウンドは修正後のコードで走ったため、`source_registry` に `gbif_kanagawa_occurrences` が正しく登録された。全テーブルの孤児検査を再実行した結果 **孤児は0件**（`x01_dwca.py` の「未登録ソースによる除外」も occurrence=0 / measurement=0）。旧名 `gbif_kanagawa` の登録行は第2ラウンド時点の重複台帳として残るため、削除せず `notes` 冒頭に `【SUPERSEDED 2026-08-29】` を付して無効化を明示した。エイリアス解決は両名を吸収する実装のまま残してあり、旧名だけが登録されている環境でも動作する。
4. **iNaturalist/GBIFのレコード単位ライセンスが未フィルタ → 本タスクで解消**: iNaturalist観察記録165,332件のうち、実測でCC BY-NC 113,284件・ライセンスなし(None) 21,058件・空文字172件（合計約82%）が非商用限定または全著作権留保のライセンスを持っていたが、`organism_records`テーブルに`license_code`相当の列が無く、`m03_organisms.py`はソースレベルの`redistributable`フラグだけを見て全件を無条件で取り込んでいた。本タスクで`organism_records`に`record_license`/`license_class`/`commercial_ok`の3列を追加し、実測値のみをマッピングして反映した（推測でopenに分類していない）。`scripts/x01_dwca.py`は既定でlicense_classが`noncommercial`/`unknown`のoccurrenceをDwC-Aから除外するようにした。詳細は`docs/LICENSE_MATRIX.md`§4.5、除外集計は`data/dwca/EXCLUDED_LICENSE.md`を参照。

### 3.3 時系列比較を妨げる注記（`cells.sqlite.notes` の `blocks_timeseries=1` 全件引用）

対象: 132 件（原文引用・要約や解釈の追加はしていない）。再追記タスクで、前回以降に `cells.sqlite` へ追加された4件（`biodic_6th_kanagawa_h16_n011` / `n_rdb2006_animals_001` / `n_rdb2006_animals_002` / `n_rdb2022_plants_001`）を追補し、`blocks_timeseries=1` の全件が本節に揃っていることを機械的に照合済み。


#### biodic_6th_kanagawa_h16
- **[biodic_6th_kanagawa_h16_n006]** (p.39, comparability) 「日本の河川の現存量は◯◯◯◯〜◯◯◯◯細胞（細胞計数の困難な藍藻などは糸状体数、以下省略）/mm²とされている。丹沢の今回の調査では◯◯〜◯◯◯◯細胞である（表1）。この数字から判明する事は、丹沢の藻類現存量は日本の河川としては値が小さいと言える。しかし、河川の付着藻の現存量は一般的に山地渓流の値は低く、平地河川では高いであるが、山地渓流の平均的な値の報告はない。」
  - 判定理由: 比較対象となる「山地渓流の平均的な値」の全国的報告が存在しないと明記されており、日本の河川一般値との比較は参照基準が不足している

## 4. FR-4.5（希少種位置一般化）検証結果

`docs/LICENSE_MATRIX.md`・`data/dwca/`検証の通り、以前のタスクでDwC-A出力の`x01_dwca.py`のFR-4.5判定ロジックのバグを修正済みだった。判定条件は「`red_list_category` の末尾括弧内コードが CR/EN/VU/EX/EW/CR+EN のいずれかに一致し、かつ緯度経度が存在し、かつ `license_class` が noncommercial/unknown でないレコード」で、該当行の座標を0.1度グリッドに丸め `dataGeneralizations`/`informationWithheld` を付与する。

**GBIF完走を反映した現在の出力では、座標を一般化したレコードは 2,080件**（`scripts/x03_verify_dwca.py` の実測値。occurrence 626,065件中）。前回集計の27件から増えたのは、DwC-Aに含まれるoccurrence自体が30,165件→626,065件に増えたことによる。

**この機能には既知の限界がある**: 一般化の判定は `organism_records.red_list_category` を経由し、これは `taxa` テーブルとの**学名による結合**で埋められる。しかし神奈川県レッドデータブック2006 由来の動物221件は原資料に学名の記載が一切なく（和名と日本語科名のみ）`taxa.scientific_name` が空欄のため、鳥類・哺乳類・魚類のレッドリスト種は学名結合できず、**該当個体の出現記録があっても一般化の対象として検出されない**。FR-4.5の実効性を上げるには和名結合または別途の学名対照表が必要である（`docs/nextstep.md` E-4 参照）。
